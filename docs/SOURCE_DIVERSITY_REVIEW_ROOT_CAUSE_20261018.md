# 반복 검토 후에도 손난로 완성본이 한 원본이 된 근본 원인

2026-10-18 사용자 질문에 대한 추가 진단. 코드·현재 SQLite·손난로 실제 timeline과 최종 QA 영수증을 읽었다. 추가 수집·재제작·운영 코드 변경은 하지 않았다. 이전 완료 보고서/원시 QA/실패 기록은 보존한다.

## 결론

핵심은 **검토와 구현의 성공 기준이 제작 중단 해소·제품 관련성·기술적 정상 출력에 집중됐고, 충분한 적합 소스를 확보했는지와 한 원본 집중을 별도 개선 판단으로 연결하지 못한 것**이다. 단순 수집 불능이나 우연한 모델 선택 하나로 설명할 수 없다.

특히 한 원본 사용 여부를 몰랐던 것이 아니다. 실제 최종 QA에 `parent_files=1`, `maximum_source_share=1.0`이 이미 있었다. 이 지표가 소스 확보·선택 개선의 계기가 되지 않았고, 최초 완료 보고에서도 사용자에게 핵심 품질 한계로 드러내지 못했다. 기술적 완료 증명은 있었지만 소스 확보·활용 품질까지 해결됐다는 증거는 없었다.

## 근본 원인 1 — 목표를 검증 가능한 결과로 충분히 나누지 않음

“편집에서 멈추지 않게 한다”는 목표는 정상 속도 연장·재사용·반응 컷 허용으로 구현·검증했다. 그러나 “더 좋은 소스 확보와 활용”을 같은 수준의 별도 결과로 확인하지 않았다. 원작10개 평가9pass/1실제 결함은 과도한 literal 기준의 조정을 검증한다. 그것만으로 우리 수집기가 다른 적합 원본을 충분히 찾거나 선택기가 균형 있게 활용한다는 증거가 되지 않는다.

## 근본 원인 2 — 단계별 승인과 전체 최적화의 차이

재고 준비는 사용할 분량/핵심 구간, 의미 검토는 각 장면의 적합성/오인, solver는 주어진 options의 비용, 최종 QA는 실제 결함을 주로 본다. 각 단계가 통과해도 “좋은 대안이 있었는가/왜 안 썼는가/다른 적합 원본을 찾을 가치가 있는가”를 연결하는 단계가 없었다.

특히 `scene_analysis.py`는 제품 오인 후보를 promoted_subject_reference 대사에 전파해 제외한다. 실제 손난로의13beat가 한 원본만 남은 것은 이 제한과 모델 순위의 결과다. 키티 제품의 직접 외형·분리 증거를 다른 손난로로 대체하지 않는 보호는 필요하다. 다만 관련 맥락의 합법적 사용 기회까지 좁혔는지는 별도로 구분해서 검토해야 한다. 전파 규칙 전체를 무조건 제거하는 해결은 부적절하다.

## 근본 원인 3 — 반복 허용에 대응하는 선택 선호·보완 판단이 부족

기존 본문 시간 중복 금지를 풀어 실제 배치 실패를 해결했다. 하지만 현재 전역 선택 비용에는 부모별 총 사용 점유율을 분산하는 항목이 없다. product 미노출/관계/화질 비용과 새 정보 보상은 남아 있으므로 주제품이 보이는 같은 원본을 계속 고르는 쪽이 유리할 수 있다. 같은 파일의 다른shot은 다른 시각 묶음으로 평가될 수도 있다.

재사용을 허용한다는 것은 가능한 편집 대안을 늘리는 결정이다. 다른 원본을 확보·활용할 가치를 평가하지 않는 결정까지 따라야 하는 것은 아니다. 이 둘을 구현/검증에서 충분히 분리하지 못했다.

## 근본 원인 4 — 측정 결과가 후속 판단·완료 보고로 이어지지 않음

`daily_quality.repetition_metrics`는 이미 부모 수와 최대 점유율을 계산한다. 그러나 반복 지표는 advisory이고 실제 blocking defect가 없으면 passed다. 이 방식 자체는 한 원본이라는 이유만으로 무조건 불합격시키지 않는 사용자 기준과 양립한다. 빠진 것은 수량/점유율을 자동 불합격으로 만드는 것이 아니라, 적합한 대안을 탐색·선택했는지 따로 확인하고 한계로 보고하는 연결이다.

앞선 기술 검수는47clip의 정상 속도·승인 구간·마스크·파일 결속을 확인했다.47clip은47개 원본이 아니며, 자연스러운 소스 분산 검증도 아니다. “최종 QA 통과·재생 완료”를 소스 다양성까지 개선했다는 의미로 확장해선 안 된다.

## 근본 원인 5 — 독립 검수에도 같은 평가 범위의 빈틈

독립 검수는 기준 상충·오인 시연·정상 속도·작업 이력·실패 반복을 실제로 찾아 고쳤다. 하지만 그 검수 요청과 완료 증거도 같은 범위에 집중했다. 여러 검수자가 같은 승인 계약을 반복 점검하면, 그 계약이 묻지 않은 질문은 여전히 빠질 수 있다.

이 부분은 독립 검수자의 능력이나 검토 횟수만의 문제가 아니라 root가 검수 범위·실영상 비교 항목·완료 보고를 설계한 문제로 판단한다. 주어진 계약을 통과했는지 보는 검수와, 그 계약이 사용자 기대를 충분히 대표하는지 비판하는 검수를 구분해야 한다.

## 새 개선 계획에 반드시 연결할 사항

1. 최신 영어5·중국어5 실제 검색/관련 승인 소스5개 수집 기준을 구현한다. 현재 문서에만 반영되어 있고 runtime 구현은 아직이다.
2. 확보→승인→의미 후보→최종 선택의 원본 수/제외 이유/실제 기여를 연결한다. 특히 선택 직전 한 원본밖에 남지 않으면 원인이 수집인지 후보 제외인지 구분한다.
3. 적합 대안이 있는 선택 반례와 실제 세 영상 전후 비교로 부모 누적 사용 비용을 검증한다. 막연한 프롬프트의 “다양하게” 지시로 완료하지 않는다.
4. 보호가 필요한 다른 제품 직접 시연과 허용된 관련 맥락을 구분한다. 최소 수량을 위해 실제 과일·무관 재킷을 주제품으로 넣지 않는다.
5. 검수자에게 “제약 충족”뿐 아니라 “수집/선택이 사용자 기대를 충족하는가, 주어진 풀 자체가 부실하지 않은가”를 별도로 점검하도록 맡긴다.
6. 완료 보고에는 실제 사용 부모 수·최대 점유율·추가 검색/확보의 유무·미사용 적합 대안·남은 한계를 표시한다. 새5개 확보 조건만으로 최종 편집도 다양해졌다고 결론내리지 않는다.

새 기준만 바꿔도5개 중1개에만 적합성이 몰리거나 solver가1개만 고르면 같은 결과가 재발할 수 있다. 따라서 **수집 최소 기준 + 후보 구성 + 선택 비용 + 실제 결과 평가/보고**를 함께 고쳐야 한다.
