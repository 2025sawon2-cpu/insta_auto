# 품질 진전 기반 제작 중단 계약

현재 한 편의 진전 판단·무진전 보류에는 이 문서의 원칙을 적용한다.
아래 SQLite/큐/worker/`quality_prepare_only`는 보존된 자동 실행기의 구현 설명이며
현재 [WORKFLOW](WORKFLOW.md)의 독립 제작 경로를 대체하지 않는다.
신규 전담 제작자는 같은 task/run에 결함·수정 가설·실제 전후 근거와 보류를
기록한다. 이 원칙을 지키려고 Studio를 재가동하거나 과거 작업을 재제작하지 않는다.

2026-10-13부터 자동 품질 보완은 고정 3회 상한 대신 실제 결함과 수정 근거로 진행한다.
`daily_quality.policy`는 기존 검토 계약을 유지하며, 하위 `progress_policy.policy`는
`quality-progress-20261013-v1`이다. 누적 `repair_round`, `render_accounting`, 기존
`max_repairs`와 설정은 역사·사용량·파일 호환성을 위해 보존하며 중단 한도로 쓰지 않는다.

## 기록과 판단

`hotpost/quality_progress.py`는 작업의 SQLite JSON 안에 결함 이력, 수정 가설,
완료한 방법, 실제 출력 비교, 최선 결과와 결정 이력을 저장한다. 초기화는 멱등적이며
기존 검토를 참조하되 선택된 편집본·승인·회계·중지 설정을 변경하지 않는다.

결함은 종류와 대본 대상에 연결한다. 대사 번호·시간 위치·이유 문구를 식별자로 쓰지
않으며, 같은 원본 장면 또는 명확히 대응하는 대사에는 이전 결함을 연결한다.
불명확한 연결은 자동 해결로 판정하지 않는다. 이전 근거와 관찰은 이력에 남는다.
검토 판단은 전체 제품 매력과 자연스러운 흐름, 구체적인 제품·기능·동작·사실 오류를
기준으로 한다. 문장마다 동일 배우·재료·사건이 나와야 한다는 조건은 추가하지 않는다.

새 수정은 대상 결함, 실제 변경, 근거, 해결될 이유를 갖는다. 장면 보완은 현재 계약에
결속한 승인 프레임·원본 구간을 사용하며, 결함과 무관한 새 파일은 편집 근거가 아니다.
표지 문구 보완은 본문 수집과 분리한다. 표지 픽셀 보완은 실제 파일 SHA·소스·사용 시각·
마스크·단독 얼굴/제품 검토와 기존 크롭 검증을 유지한다. 오디오 보완은 승인 목소리를
유지하고 해당 출력의 실제 PCM 길이·파형 위치 오류에 연결한다.

새 파일의 표지 효과가 미확인인 경우 정상 편집 분석·사용 구간 선택·표지 검토를
`quality_prepare_only`로 실행한다. 영상 렌더 전에 반환하며 음성과 보완 사용량을
증가시키지 않는다. 실제 사용될 표지와 선택 계획을 SHA·현재 입력에 결속해 저장하고,
같은 실패 입력은 다시 검토하지 않는다. 서명된 계획이 소실·변경되면 근거 대기로
남긴다. 본문 준비 완료를 얼굴 없는 표지 확보로 오인하지 않는다.

큐 등록, worker 실행 전, 실제 장면/표지 선택 후 렌더 직전에 각각 검사한다.
원 URL/알려진 부모 SHA·구간·순서·관련 마스크/기하·표지·대본·음성의 실제 입력을
비교하고 완료된 같은 방법을 차단한다. 코드 계약 해시는 캐시 호환성에 사용하지만
새 품질 근거로 사용하지 않는다. A→B→A도 보존된 전체 방법 이력으로 차단한다.

검토에서 해결된 결함과 새 중요 결함을 따로 기록한다. 점수 상승·지적 개수 감소만으로
개선을 인정하지 않으며, 표지 변경만으로 본문 결함을 해결했다고 판정하지 않는다.
회귀가 섞인 결과는 최선 결과를 덮지 않는다. 최선 결과는 검토 후보 기록이며 사용자가
선택한 현재 편집본을 자동 교체하지 않는다.

동일 출력의 판정 상충은 전체 영상을 통과할 때까지 다시 질문하지 않는다. 정상 검토
경로에서 해당 구간의 새로운 밀집 프레임으로 한 번 확인하고 영수증을 저장한다.
같은 출력·결함의 확인은 재사용한다. 파일 소실·근거 부족·계속된 불일치는 근거 대기로
남기며 렌더나 회계를 증가시키지 않는다.

## 검색·대기·복구

검색 이력은 실제 플랫폼·검색어/이미지·페이지/커서/offset 범위를 보존한다.
같은 검색어라도 실제 새 범위는 허용하고, 표현이 달라도 같은 후보 URL/원본 구간은
기존 후보 중복 제거와 편집 방법 검사에서 차단한다. 현재 검색기의 자동 페이지 이동
기능은 없으므로 가짜 페이지 번호를 만들어 반복 검색하지 않는다.

동일 원문 제품 근거의 모델 검색어 계획은 `data/source-query-plans/`에 저장해 유한한
근거 있는 검색 범위로 유지한다. 새 날짜·회차·작업 ID·모델 표현만 바뀌어 범위가 늘지
않는다. 실제 제품/원문 근거가 바뀌면 새 계획을 만든다. 사용한 방법의 실패 후에는
미사용 범위만 탐색하고, 관련 근거와 방법이 소진되면 `scene_wait`로 대기한다.

모델/브라우저 정상 대기·접근 미시도·429·수동 중지는 콘텐츠 무진전과 분리한다.
실제 새 보완 렌더만 사용량에 1회 추가한다. 첫 렌더는 baseline이고 보완 사용량 0이다.
중복 완료·재시작·no_render에서 기록과 회계를 중복시키지 않는다.

기존 `exhausted`나 `failed` 작업은 초기화·재시작으로 해제하지 않는다. 명시 재개 시
관련 실제 새 방법과 현재 장면 증거를 별도 평가하고, 유효한 경우에만 과거 중단을
`stop_history`에 보존한 채 진행한다. 설정 한도를 올리거나 과거 회계를 초기화하지 않는다.
서비스 반영은 전체 실행/대기 큐 0와 소유 프로세스 확인 후 수행한다.

## 2026-10-14 독립 재검증 보완

정책 이름과 과거 회계는 보존했다. 최근 구현도 정확하다고 전제하지 않고 수집부터
전달까지 실제 호출자·저장 경계를 다시 점검했다. 상세 판단·검증 한계는
[전체 흐름 감사](workflow_reliability_audit.md)에 있다.

- 제작 큐 claim마다 소유 토큰을 바꾼다. 완료·실패·대기·중간 상태·체크포인트·편집
  요청 쓰기·음성 저장 모두 현재 claim에 결속한다. 중복/늦은 완료는 결과·회계·이벤트를
  다시 쓰지 않는다. 정상 worker와 예약 복구 도구는 같은 품질 방법 permit를 사용한다.
- 편집 응답은 하위 runner의 전체 요청 서명(action/output_dir 포함)을 확인한다.
  신규 수용 산출물의 SHA를 보존하고 재사용 시 실제 파일을 확인한다. 과거 부모 수용
  해시가 없는 영수증의 소급 무결성을 추정하지 않는다.
- 검수 시작/종료, 결과 수용, 최종 완료, 완료본 공유에서 실제 render/plan의 동일성을
  확인한다. 파일 존재·edit ID·passed 문자열만으로 검증을 승계하지 않는다.
- 실제 자막 문구/시간축을 출력 동등성에 포함한다. 동일 부모 영상의 subframe 이동은
  실제 노출 근거와 비교하며 날짜·회차·작업 ID처럼 새 방법으로 세지 않는다. 실제 다른
  구간·노출·검토 근거는 허용한다. 과거 실패 이력의 추가 필드를 보완해도 이력은 지우지 않는다.
- 소스 수집의 별도 연속 3회 무성과 중단도 없앴다. 고정 계획·소비한 실제 검색 범위와
  확정 검사 탈락 URL 이력으로 반복을 차단한다. 네트워크 미시도/접근 대기는 검사 실패와
  구분한다. 접근이 회복되면 미소비 범위부터 이어가고 실제 범위가 소진되면 보류한다.
- 품질 재수집의 접근 대기는 같은 작업의 not_before 대기로 저장한다. 수신 파일과
  완료한 시각 검토 체크포인트를 유지하며 품질 실패·보완 렌더 사용량으로 충전하지 않는다.
- 짧은 소스의 고정 4초 하한은 품질 조건에서 제거했다. 양수·유한 길이/실제 영상과
  장면 승인 검사는 유지한다. 핵심 장면 목표 초수는 실제 승인 구간 합집합으로 계산하며
  같은 2초 장면을 두 번 넣어 4초로 만들지 않는다.
- 새 대본 보완은 지적 개수를 비교하지 않는다. 비교 판단과 실제 중요 사실·복사 결함의
  회귀를 확인하며, 같은 잘못된 수치의 표현 변경을 새 사실 오류로 오인하지 않는다.
  기존 잘못된 수치의 지적은 유지한다. 기존 선택 대본·음성은 변경하지 않는다.
- 완료 작업에 남은 자동 collect_sources 큐는 paused로 보존한다. 명시적인 추가 검색과
  사용자 수정 요청은 별도 경로로 처리하고 이미 실행 중인 수신 결과는 보존한다.
- `service_retries`는 실제 모델 처리 실패 시도 이력이며 품질 상한이 아니다. 과거 3회 이상이어도
  현재 미시도 준비·용량 대기는 queued/not_before로 보존한다. 실제 호출은 공통 용량 gate,
  Retry-After와 동일 요청 ID를 따르고, 확정 설정·인증·시작 종료 문제는 별도 조치를 표시한다.
  `ModelServiceUnavailable.attempted=False`는 새로운 모델/TTS 생성 실패 시도가 아니라는 뜻이다.
  기존 요청의 상태·음성 파일 GET는 실제 HTTP 전송이 있어도 이 대기 분류를 사용한다.
  HTTP 호출량과 새 생성/품질 보완량은 같은 회계가 아니다. 수동 제작의 응답 불명 TTS 제출도
  작업·선택 대본에 결속한 안정 generation_key로 기존 요청을 재사용한다.

시간 설정은 용도별로 유지한다. HTTP 연결/응답과 앱 창 확보는 단계 응답 감시이며,
다운로드/ASR/FFmpeg/현재 기본 native export는 유효 결과 이후 무진전 감시다. 요청 간격,
429 휴식, 서비스 소유 큐 대기는 콘텐츠 실패가 아니다. Windows 예약은 PT0S로 총 경과
시간에 의한 강제 종료를 하지 않으며 개별 요청 감시·독점 실행·사용자 접근 제한은 유지한다.

## 검증 경로

독립 반례는 `test_quality_progress_independent.py`,
`test_quality_progress_policy_independent.py`, `test_search_scope_progress_independent.py`에 있다.
기존 `test_daily_quality`, `test_cover_scope_recovery`, `test_render_contract_queue*`,
`test_repair_render_accounting`, `test_quality_render_baseline_independent`,
`test_refresh_resume`, `test_daily_quality_scope`, 실제 Studio 큐/worker 회귀를 함께 실행한다.
화면은 `web/studio-detail.js`의 품질 보완 현황에서 결정 이유·잔존/해결 결함·실제 보완
사용량·다음 수정 근거를 확인한다.
