# 2026-10-18 오전 자동 제작 편집 중단 원인 종합 조사

조사 시각: 2026-10-18 12시대 KST. 대상은 오늘 07시 수집이 생성한 상위 3개 작업이다. 운영 DB는 읽기 전용으로 조회했고, 보존된 선택 요청을 메모리 복사본에서 계산했다. 신규 수집·모델·음성 합성·렌더·운영 재시작·작업 재개·운영 코드 변경은 하지 않았다. 별도 감사 자료와 이 보고서만 작성했다.

## 결론

**편집에서 멈추는 원인이 아직 있다. 오늘 3개 모두 첫 완성 MP4를 렌더하기 전 장면 배치에서 실패했고, 복구 가능한 장면 부족을 일반 실행 오류로 처리하면서 자동 제작을 종료했다.** 소스 검토를 전부 느슨하게 하거나 검색 수만 늘려 해결할 문제는 아니다.

공통 흐름은 다음과 같다.

1. 수집기는 승인 영상의 총 분량과 핵심 기능 영상 최소 4초를 확인해 준비 완료로 판단한다.
2. 대본별 의미 분석에서 특정 구간에 쓸 수 있는 후보가 더 좁아진다. 제품·색상·기능별 수요와 후보 길이를 수집 완료 판정은 검사하지 않는다.
3. 현재 전역 선택기는 대사 조각 전체 길이를 한 승인 장면에 넣고, 같은 원본의 사용한 시간은 다시 쓸 수 없도록 배정한다. 오늘 입력 3개는 이 조건 아래 실제로 배정 불가능했다.
4. 선택 실패의 구조화된 원인이 사라져 `RuntimeError` 문자열만 주 실행기에 전달된다.
5. 기존 추가 장면 확보 경로가 호출되지 않고 `automation.active=false`, `daily_quality.pending=failed`로 끝난다.

따라서 **준비 완료 판정과 실제 편집 가능성의 불일치**, **새 선택기의 실패와 기존 복구 경로의 단절**이 가장 먼저 고칠 공통 원인이다. 별도로 가능한 배정을 놓치는 탐색 결함과 오류 오분류도 재현했다.

## 1. 수집 완료를 편집 가능으로 간주하는 계약의 공백

`hotpost/source_coverage.py:106`의 `coverage_goal()`은 승인 원본 시간 합집합과 핵심 기능 시간 합집합을 계산한다. `hotpost/studio_sources.py:94`의 준비 판정은 총량 및 핵심 최소량을 사용한다. 원본 중복 계산을 피하는 개선은 적용되어 있다. 그러나 다음은 검사하지 않는다.

- 대본의 어느 부분이 어느 제품·색상·기능을 실제로 요구하는가.
- 해당 부분의 후보가 대사보다 긴가.
- 여러 대사가 같은 짧은 후보를 경쟁해서 전체 동시 배정이 불가능한가.
- 의미 분석 후 남은 후보만으로 원본 시간 비중복 배정이 가능한가.

가방의 준비 분량 20.4초에는 가방이 나오지 않는 의류 매장·재킷 맥락 8초가 포함된다. 실제 대본 선택지에는 그 8초가 하나도 들어가지 않는다. 전체 선택지의 합집합은 12.4초인데 출력은 15.08초다. 총량에 여유가 있다는 숫자만으로 해결되지 않는다.

음성 제작과 소스 확보의 병행 자체는 시간을 줄이지만, 음성과 의미 분석이 완성된 뒤 더 정밀한 배치 가능성 검사로 수집의 임시 준비 판정을 갱신해야 한다. 지금은 이 인계 검사가 빠져 있다.

## 2. 기능별 수집 승인과 제품 전체 의미 제외 범위가 다름

텐트에서는 바닥을 지면 위에 띄우는 기능이 같은 녹색 침상형 텐트를 수집 단계에서 핵심 기능 영상으로 승인했다. 반면 의미 순위 모델은 차량 뒤 주황색 상자형 제품과 구조가 다르다는 이유로 차량 장착 대사뿐 아니라 바닥 이격 혜택·마무리까지 모두 후보에서 제외했다.

실제 프레임에는 차량형과 독립 침상형의 구조 차이가 있다. 따라서 독립형 영상을 차량 장착의 직접 시연으로 사용할 수 있다고 결론 내리지 않았다. 확정 문제는 **수집이 기능별로 승인해 센 분량을, 배치에서는 제품 전체 기준으로 제외하면서도 부족을 정상적으로 되돌려 주지 않는다는 점**이다. 혜택의 관련 예시로 쓸 수 있는지는 실제 컷의 맥락을 판단해야 한다.

완화된 레퍼런스 기준은 실제 텐트 순위 모델 입력에 포함되어 있었다. 단순히 서버가 옛 지침을 사용했다고 설명할 수 없다. Python 후처리 `hotpost/scene_analysis.py:247`도 각 beat의 incompatible 후보를 합쳐 다른 promoted beat에 전파하지만, 이번 텐트는 모델 원응답부터 같은 후보를 반복 제외했다. 전역 union 하나를 지우는 것만으로 고쳐지지 않는다.

제품 전체 불일치와 특정 특징의 불일치를 구별하고, 수집 영수증·순위 판단·대본 구간별 수요에 동일한 범위를 전달해야 한다. CTA나 일반 혜택까지 제품 전용 후보를 요구하는 정책을 유지한다면 수집 준비 계산에도 그 시간이 들어가야 한다.

## 3. 짧은 대사 조각과 승인 구간 길이를 함께 계획하지 않음

몽벨 더블백은 독립적인 부족이 여러 개 있다.

- beat 3 “이 주황색에 눈이 가요”: 1.4467초, 유일 후보 `shot-2-1`은 1초.
- beat 14 “이 색을 대보고 싶어요”: 1.2733초, 같은 1초 후보뿐이다.
- beat 6과 13: 각각 1.06초·1.26초. 후보 3개 중 2개는 1초라 길이가 모자라며, 남은 1.4초 후보 하나를 둘이 공유해야 한다. 합계 2.32초를 담을 수 없다.
- 모든 의미 후보의 합집합 12.4초가 전체 수요 15.08초보다 작다.

따라서 주황색 장면 한 구간만 늘리거나 선택기 탐색만 늘려도 해결되지 않는다. 추가 검토·관련 장면 확보가 어떤 제품/특징과 어느 길이를 채워야 하는지 계산해서 요청해야 한다.

손난로의 최소 부족 약 0.037초는 과거 0.000000000000002초 같은 덧셈 오차가 아니다. 30fps 기준 약 1.11프레임이며, 실제 제품 전용 승인량보다 수요가 크다. 다만 이 정도 차이로 전체 자동 제작이 끝나는 것은 복구 설계의 문제다. 승인 경계 밖을 오차로 허용하는 대신, 프레임 단위 길이 계산과 해당 구간의 정상 보완으로 처리해야 한다. 작은 승인 구간 추가만으로 전체 조각 배치까지 가능해진다는 보장도 없으므로 재배치 검사가 필요하다.

## 4. 탐색 폭 128과 원인 오분류도 실제 결함

`auto_capcut/core/studio_story_selection.py:41`의 `beam_width=128`은 매 대사 구간 뒤 비용이 낮은 부분 편집안 128개만 유지한다는 뜻이다. 외부 영상 검색 예산·API 비용 한도·모델 서버 한도가 아니다.

실제 손난로 요청을 변경하지 않고 계산했다.

| 유지하는 부분 배치 수 | 결과 |
|---:|---|
| 128, 운영 기본 | beat 12에서 실패. 이전에 후보를 버렸으므로 budget 오류로 표시 |
| 1,024 | beat 14에서 실패 |
| 100,000 | 실제 생성 상태 최대 11,216개로 잘림 없음. 누적 57,669개를 검사한 뒤 beat 15에서 분량 부족으로 실패 |

전체 입력에는 독립적인 분량 부족 증명이 있으므로 숫자만 키워도 완성되지 않는다. 텐트도 빔 가지치기 전 이미 실패한다.

반면 손난로의 마지막 CTA 두 구간만 진단 목적으로 제외한 앞 13개 구간은, 같은 장면·같은 의미 후보로 1,024 폭에서 정상 배정되고 기존 freeze 검증을 통과한다. 운영 기본 128은 이 가능한 경우도 놓친다. 이 대조 실험은 제작 원고를 줄이자는 제안이 아니다. **미래에 필요한 희소 후보를 고려하지 않는 비용순 가지치기의 오탐**을 분리한 증거다.

선택기는 앞에서 한 번이라도 후보를 잘랐다면 이후 어떤 이유로 막혀도 `search_budget_exhausted`로 표시한다(`studio_story_selection.py:98`). 실제 부족의 증명과 탐색 미완료를 구분하지 않는다. 현재 생성 후보 상태의 완전 열거는 가능한 모든 연속 시작 시간을 전부 조사한 것은 아니지만, 전체 요청의 부족은 별도의 합집합 용량 증명으로 확정된다.

## 5. 실패 사유가 복구 경로로 전달되지 않아 자동 제작 종료

현재 경로는 아래와 같다.

```text
select(): ValueError + 메모리에만 selection_diagnostics
  → studio_runner.py: 실패 JSON에 status/error/request_sha256만 저장
  → hotpost/studio_runtime/editing.py:250: RuntimeError(error 문자열)
  → lifecycle.py: 일반 실패 분기
  → daily_quality.py:307 fail_daily_quality()
  → attention / pending=failed / automation.active=false
```

주 실행기에는 이미 `QualitySceneGap → handle_daily_scene_gap()`이라는 준비 부족 처리 경로가 있다. 이번 예외는 그 타입과 구간별 증거를 갖고 오지 않아 해당 분기로 들어가지 않는다. 실패 JSON 3개 모두 실제로 `status`, `error`, `request_sha256`만 있다. 막힌 beat, 필요한 제품/특징, 부족 길이, 검색 상태, 가능한 대안이 사라진다.

품질을 위해 실제 잘못된 영상을 멈추는 기능은 필요하다. 하지만 이번에는 “부족한 장면을 보완해야 함”과 “프로그램 실행 오류”를 같은 경로로 보내어 기존 보완 자동화가 작동하지 않는다. 같은 입력을 재시도하는 방식은 이 계약 공백을 고치지 못한다.

`product-story-global-v3`는 `studio_diversity.py:69`에서 별도 선택기로 즉시 분기한다. 기존 다른 선택 경로의 재생·정지 화면 대안이 새 전역 경로에도 적용된다고 볼 수 없다. 이 보고서는 원본 반복·정지 화면을 일괄 허용하라고 권고하지 않는다. 허용할 표현과 증거 보존 기준을 정한 뒤 해당 정책과 수집·배치·실제 QA를 함께 검증해야 한다.

## 왜 그동안 개선했는데 남았는가

**개선한 기능의 범위와 검증한 입력이 이 중단 경로 전체를 덮지 못했다.** 구현·실험·검증 완료를 나누어 봐야 한다.

| 이전 개선/검증 | 확인된 효과와 이번에 남은 경계 |
|---|---|
| 총 소스 수·플랫폼 강제 조건을 분량/선호로 변경 | 오늘도 3개 소스로 준비 완료까지 진행했다. 그러나 대본별 후보 분량이 충분한지는 보장하지 않는다. |
| 같은 파일의 짧은 승인 구간 복구 | 선반 사례에서 승인량 증가를 실측했고 오늘 텐트에도 복구 시도 영수증이 있다. 이후 의미 분석이 만든 특정 후보 부족을 다시 복구로 보내는 연결은 별개다. |
| 레퍼런스 5개와 엄격도 비교 | 감사 문서는 당시 필요한 구간의 운영 자동화를 미구현으로 명시했다. 후속 로컬 복구 구현도 모든 의미 배치 실패의 자동 복구를 검증한 것은 아니다. |
