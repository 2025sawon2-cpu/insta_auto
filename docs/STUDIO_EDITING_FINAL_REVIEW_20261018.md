## 범위와 현재 결론

주 담당과 별도인 에이전트가 `AGENTS.md`, `STUDIO_EDITING_AUDIT_20261018.md`, 변경 전 코드 ZIP·보존 기준선, 배포 영수증과 현재 변경을 읽었다. 목록 API, 웹 폴링, 수동 표지와 조상 영상, QA·과거 버전 다운로드, 품질 재시도, 목소리 변경 후 수동 표지 계승을 검토했다.

**독립 검토에서 발견한 품질 재시도와 웹 상세조회 경합은 현재 파일에서 보완됐고 격리 반례도 통과했다.** 목록·수동 표지·QA·workflow Python 회귀128개, 격리 브라우저 회귀38개, 후속 보완 회귀5개가 통과했다. 운영 상태나 코드·설정·큐·브라우저 프로필은 변경하지 않았다. 허용된 임시 테스트 산출물과 이 문서만 생성했다.

이 결론을 새 speed1.05 영상의 제작 완료 또는 현재 모든 최신 코드의 운영 로딩 완료로 해석하지 않는다. 아래 실제 상태와 배포 한계를 분리한다.

## 독립 발견과 보완 재확인

### 오래된 품질 작업 재시도가 현재 버전 상태를 덮는 문제

초기 변경은 일반 edit 재시도에는 현재 음성을 확인했으나 `quality_review`·`quality_reedit`에는 현재 edit/승인 voice 대조가 없었다. 임시 DB의 정상 `test_daily_quality.ready` fixture에서 과거 실패 QA를 남기고 현재 run·edit·voice를 바꾼 뒤 과거 job을 명시 재시도했다. 새 script가 같다는 이유로 과거 job이 queued가 되면서 현재 status와 daily_quality.pending이 quality_review로 덮였다. 늦은 실제 QA 수용을 뒤에서 막는 것과 별개로 현재 제작 상태가 손상될 수 있었다.

현재 파일은 두 품질 작업의 payload.edit_id와 현재 edit_id, payload.voice_id와 현재 approved_voice_id가 일치해야 재시도를 허용한다. 같은 독립 임시 DB 반례를 다시 실행해 다음을 확인했다.

- `Conflict`로 거부.
- 작업 state 전체가 이전 값과 동일.
- 과거 job은 failed를 유지.
- 새 회귀 `test_old_quality_retry_cannot_overwrite_a_new_video_version` 통과.

### 느린 상세조회 중 작업 전환 경합

목록 요약 후 선택 상세를 조회하는 초기 `refresh()`는 요청할 때와 응답을 배열에 넣을 때 모두 변하는 전역 selectedId를 사용했다. A 응답을 기다리는 동안 B를 선택하면 A 내용을 B 위치에 넣을 수 있는 경계였다.

현재 `web/studio.js`는 `detailId`를 캡처해 동일 작업 행에만 결과를 반영한다. 격리 fixture 브라우저에서 A 상세 응답을 보류하고 A를 닫은 뒤 B를 열어 B 제목 표시를 확인한 후 늦은 A 응답을 수용했다. B 카드1개·B 드로어 열림이 유지됐다. 이 테스트는 `studio.test`의 가짜 API만 사용했다.
