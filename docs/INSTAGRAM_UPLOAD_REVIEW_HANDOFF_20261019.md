# 인스타그램 업로드 프로세스 검토 계획

## 목적과 이번 요청 범위

완성 영상이 우리 인스타그램 게시물로 올라가고, 의도한 상품 링크와 리틀리 자동화에 정확히 연결되는 전체 과정을 새 세션에서 검토한다. 사용자의 현재 요청은 계획과 인계 준비다. 이 문서를 읽는 것만으로 실제 게시·댓글·팔로우·DM·리틀리 등록이나 구현을 시작하지 않는다. 새 세션에서는 사용자가 요청한 검토부터 수행하고, 구현·실증 요청이 주어지면 그 범위에 맞춰 이어간다.

영상 제작과 게시 후속 처리는 별개 상태로 관리한다. 업로드 실패를 이유로 완성된 영상·대본·음성을 다시 만들지 않는다. 영상 제작의 내부 오류 자동 복구 방침을 외부 댓글·게시의 무조건 재전송으로 확대하지 않는다.

## 기존 크롬 연결 정보

관리 화면 접근을 확인했으며, 리틀리에 연결된 인스타 계정명·게시 권한·파트너스 연결·실제 자동화 등록 성공까지 검증한 것은 아니다. 이 항목들은 새 세션에서 필요한 범위만 읽기 전용으로 확인한다. 관리 화면이 이미 열려 있으므로 근거 없이 재로그인을 요구하지 않는다.

### 새 세션 연결 절차

1. 프로젝트의 `hotpost.config.load_settings()`로 현재 설정을 읽는다.
2. `hotpost.source_browser_runtime.endpoint(settings)`로 현재 제작용 프로필의 CDP 주소를 구한다. 이 함수는 `DevToolsActivePort`와 실제 브라우저 식별자를 대조한다. 7076은 관찰 당시 값이며 하드코딩하지 않는다.
3. 반환된 주소에 `playwright.chromium.connect_over_cdp(address)`로 연결한다. 연결만으로 새 창이나 프로필을 만들지 않는다.
4. 기존 탭 중 호스트 `app.litt.ly`, 경로 `/marketing/instagram`인 관리 탭을 식별한다. 탭 ID는 관찰 기록이므로 현재 URL·화면으로 다시 확인한다. 인스타그램도 같은 브라우저의 기존 탭과 실제 로그인 계정을 확인한다. 복수 계정/탭이면 게시 대상을 추정하지 않는다.
5. 주소나 탭이 없으면 현재 프로필·프로세스·연결 상태부터 진단한다. `ensure_browser()`나 복구 도우미를 통해 새 창 생성·기존 탭 이동·브라우저 재시작을 자동 수행하지 않는다.
6. 검사 후 Playwright 연결만 해제한다. 연결한 `browser`/`context`에 `close()`를 호출해 사용자의 창을 닫지 않는다. 실제 화면을 조작할 단계에서는 기존 수집 작업과의 브라우저 잠금·직렬 처리 계약을 먼저 확인한다.

이전에 안내했던 `9223`은 이번 인계의 연결 대상이 아니다. 당시 다른 자동화 크롬이 `127.0.0.1:9223`을, 별도로 연 `C:\Codex\Chrome-Instagram` 크롬이 `[::1]:9223`을 사용해 잘못된 창을 조회한 이력이 있다. 사용자가 이후 원래 제작용 크롬으로 정정했으므로, 포트 번호나 `localhost`만으로 창을 선택하지 말고 위 제작용 프로필에서 주소를 확인한다. 다른 크롬을 종료하거나 해당 설정을 변경할 필요는 없다.

## 확인한 현재 구현

- `hotpost/monetization.py`: 완료 영상과 선택 대본에 연결해 상품 확인, 제휴 링크, 본문, 리틀리 설정을 진행한다. 리틀리 등록 후 `awaiting_post`에서 기다리며 `inspect_post(task_id, post_url)`로 실제 게시물 연결을 확인한다.
- `hotpost/post_publish.py`: 게시글 본문과 DM 문구를 준비한다. 이름과 달리 이 파일 자체는 동영상 업로더가 아니다.
- `hotpost/monetization_browser.py`: 레퍼런스 댓글·수신 DM·리틀리 설정·게시물/발송 확인 경로가 있다. 여기의 `게시/Post` 클릭은 레퍼런스 댓글 제출이며, 우리 릴스 업로드로 혼동하지 않는다.
- `hotpost/monetization_store.py`: 계정별 순차 처리, 외부 동작 시도 기록, 다음 게시물 예약 슬롯을 관리한다.
- `hotpost/monetization_completion.py`: 영상 완료 전환을 후속 처리에 전달하는 영속 기록이 있다.
- `hotpost/monetization_http.py`, `web/monetization.*`: 연결 설정과 단계별 동작을 제공한다. 확인한 HTTP 동작에는 동영상 업로드·발행 동작이 없다.

따라서 첫 핵심 검토는 **리틀리 설정 뒤 실제 인스타 업로드·발행을 맡는 실행 경로가 다른 곳에 존재하는지, 없다면 어떤 연결이 빠져 있는지**다. 코드·fixture 검증과 실제 계정에서의 성공은 구분한다. 10월 16일 구현 문서의 연결 부재 기록은 당시 상태이므로 새 세션에서 현재 연결을 다시 확인한다.

## 목표 처리 순서

1. 실제 최종 영상과 승인 대본·음성·검수 결과의 연결을 확인한다.
2. 기존에 확인한 상품 결과가 있으면 재사용하고, 필요한 레퍼런스에만 기존 규칙에 따라 상품 정보를 확인한다.
3. 본인 쿠팡파트너스 링크를 발급하고 실제 상품·옵션 일치를 확인한다.
4. 선택 대본 기반 본문, 제휴 안내, 표지, 게시 계정을 묶어 게시 패키지를 만든다.
5. 리틀리의 해당 계정에 다음 게시물 자동화를 하나 준비하고 저장 내용을 확인한다.
6. 정확한 계정에 지정한 MP4·표지·본문을 업로드하고 발행한다.
7. 실제 게시물 ID와 URL, 계정, 영상·표지·본문 반영을 확인한다.
8. 리틀리 자동화가 바로 그 게시물과 상품 링크에 연결됐는지 확인한다. 확인 후 다음 상품의 예약 슬롯을 연다.
9. 실제 발송 근거가 있을 때만 DM 전달 완료로 기록한다. 게시 완료·자동화 연결 완료·DM 전달 완료를 각각 구분한다.

제휴 상품이 없는 요리·도안 등 콘텐츠는 상품 링크를 억지로 만들지 않는다. 기존 비상품 경로의 유무와 게시 가능 조건을 검토하고, 필요한 정책 결정으로 명시한다.

## 새 세션 검토 순서

### 현황과 계정 확인

- `AGENTS.md`, 아래 참고 문서, 위 진입점과 관련 테스트부터 읽는다.
- 로컬 서버의 요약 API와 필요한 단일 작업만 조회한다. 전체 상세 작업 목록을 가져오지 않는다.
- 게시 대상 인스타 계정, 기존 Chrome 연결, 리틀리 연결 계정, 파트너스 연결 여부를 읽기 전용으로 확인한다. 인증키 값은 채팅·로그에 출력하지 않는다.
- 위의 기존 크롬 연결 절차를 따른다. 리틀리 관리 화면 접근 성공과 인스타 게시 계정·권한 확인을 구분한다.
- 기존 업로드·외부 시도·리틀리 슬롯이 있는지 먼저 확인해 새 세션이나 새 작업 ID로 중복 실행하지 않는다.
- 계정별 순서, 즉시 게시/예약 게시, 표지와 본문 규칙 등 실제로 미정인 사항만 정리한다. 이미 확정된 규칙은 다시 묻지 않는다.

### 실행 구조와 책임 범위 설계

- 영상별 영속 담당자를 유지하면서 업로드 실행을 인계할지, 별도 게시 담당자에게 완료 증거와 책임을 명시적으로 넘길지 기존 구조와 비교해 결정한다.
- 게시 패키지에 task/run/edit, 실제 MP4·표지·본문 해시, 인스타 계정, 상품·옵션, 제휴 URL, 리틀리 자동화 ID를 결속한다. 영상 또는 본문이 바뀌면 이전 게시 준비를 그대로 쓰지 않는다.
- 최소 상태: 게시 준비, 업로드 중, 플랫폼 처리 대기, 발행 결과 확인 중, 게시 확인 완료, 리틀리 연결 확인, 발송 확인, 접근 복구 대기, 내부 복구, 사용자 중지.
- 외부 제출 전 시도와 소유권을 저장한다. 제출 후 응답이 끊겼으면 결과 조회부터 하며 새 게시물을 바로 만들지 않는다.
- 계정당 다음 게시물 슬롯 하나를 유지한다. 사용자가 별도 게시물을 올린 경우에도 의도한 상품과 다른 게시물이 연결되는 것을 감지한다.
- 현재 승인된 동일 Chrome 세션 경로와 기존 설정을 우선 조사한다. API 대안을 제안한다면 최신 공식 문서와 실제 계정 권한·지원 기능을 확인한 뒤 비교하고, 로그인/CAPTCHA를 다른 세션이나 계정으로 우회하지 않는다.

### 화면 표시

- 게시물에서 현재 단계, 마지막 실제 진전, 자동 재개 대기 이유, 복구 시도, 게시 결과 링크를 짧게 표시한다.
- 진행 애니메이션은 실제 실행/대기 상태에 연결한다. 멈춘 작업을 계속 작업 중인 것처럼 표시하지 않는다.
- 영상 완료와 게시 완료를 별도로 표시하고, 리틀리 등록만으로 DM 전달 완료라고 표시하지 않는다.

### 검증과 단계적 실증

- 먼저 복제 상태·fixture로 외부 부작용 없이 상태 전이, 중복 방지, 장애 복구를 시험한다.
- 다음으로 실제 로그인 화면과 입력 경로를 읽기 전용으로 확인한다.
- 실제 게시가 승인된 실행 단계에서는 검수 완료된 한 영상으로 업로드부터 게시 URL·리틀리 연결까지 확인한다. DM 발송 검증에 별도 댓글/메시지가 필요하면 그 행위의 사용자 지시를 확인한다.
- 한 건의 실제 성공 증거를 확보한 뒤 같은 계정의 세 영상을 순차 처리하는 검증으로 확장한다.

## 유지할 기존 규칙

- 상품 확인을 위한 레퍼런스 댓글·DM 흐름은 같은 계정·레퍼런스당 한 번이다. 실패하면 오류를 남기며 새 job이나 세션으로 재댓글하지 않는다.
- 직접 상품 링크형과 팔로우 확인형은 기존 두 경로를 따른다. 임의 DM 발송을 추가하지 않는다.
- 쿠팡 링크는 본인 파트너스 API 경로와 실제 상품·옵션 검증을 유지한다.
