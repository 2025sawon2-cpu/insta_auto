## 실행 흐름과 완료 의미

`상품 확인 → 제휴 링크 → 본문·게시 패키지 → 리틀리 등록 → awaiting_post`
까지 기존 자동 후속 실행을 유지한다. 인스타 게시는 별도 `publish` 동작으로
실행한다. 이번 구현을 이유로 자동 게시 설정을 켜거나 과거 완료본을 재개하지 않는다.

게시 단계는 `uploading → submitting → platform_processing → awaiting_confirmation`
으로 기록한다. 지정 MP4·표지 파일의 실제 선택, 본문 입력과 계정 표시를 확인한 뒤
Share를 한 번 호출한다. 지원하지 않는 작성 화면이나 중복 입력은 추정 클릭하지 않는다.
파일은 제출 직전과 결과 수용 때 다시 검증한다. 실행 소유권은 해당 시도 ID에 고정한다.

제출 중 끊김은 `unknown`으로 보존하고 새 업로드를 차단한다. 실제 게시물 주소의
읽기 전용 확인은 허용하며, 저장된 업로드 결과 URL이 있으면 다른 URL은 거부한다.
리틀리 상세의 실제 게시물 링크·계정·상품 링크와 우리 게시물의 영상 요소·본문을
확인해야 계정 슬롯을 해제한다. 실제 성공 발송 기록은 그 뒤 별도로 확인한다.

리틀리 응답 유실도 `unknown`으로 남긴다. 해당 시도 ID와 패키지 SHA에 결속된
답글 기준값이 있고, 기존 상세의 계정·모드·모든 댓글·DM·버튼·링크·답글 수·상태가
일치할 때만 재생성 없이 수용한다. 기준값이 없는 시도를 임의로 복원하지 않는다.

추가 API: `POST /api/monetization/{task}/publish`,
`POST /api/monetization/{task}/inspect-littly`.
화면은 백엔드의 `publication_supported`를 확인하므로 구형 프로세스에는 새 게시
버튼을 노출하지 않는다. 영상 완료·리틀리 등록·게시 연결·실제 DM 전달을 구분한다.

## 운영 적용

메인 8775 서버에는 제작 queued 2건이 있어 재시작하지 않았다. 인스타 게시 지원
백엔드는 후속 작업 전용 **3235 서버**에 적용했다. 실제 리스너 PID **29704**의
새 프로세스에서 관련 모듈 8개의 로드 경로·SHA가 저장 코드와 일치했다.
완료 감시/제작 worker는 보조 서버에서 실행하지 않는다.

수익화 DB를 백업했고 records/effects/events/slots/configuration 전후 행이 모두
동일하며 `quick_check=ok`다. 외부 effect 추가는 0건이다. 기존 메인 PID 43520,
브라우저·VoiceBench와 제작 큐는 보존했다. 최초 배포 확인은 Windows venv launcher와
실제 Python child의 PID 차이로 실패했으며, 실제 포트 리스너와 모듈 로드 영수증을
대조해 확인을 수정했다. 이 확인 때문에 서버를 다시 시작하지 않았다.

운영 근거: 같은 증거 폴더의 `deployment.json`, `helper-expected.json`,
`helper-loaded.json`, `monetization-before.sqlite3`.

## 남은 실증 범위

실제 인스타/리틀리 작성 DOM, 본인 API 응답, 실제 게시 URL·리틀리 연결과 실제 DM
성공은 이번에 검증하지 않았다. 고정 UI 계약과 다른 실계정 화면은 해당 단계에서
중지한다. UI fixture 통과를 실계정 업로드 성공으로 보고하지 않는다.

게시 영수증의 `media_verified=false`는 공개 게시물의 재인코딩된 영상·표지 자체를
로컬 원본과 비교한 검증이 아직 없다는 뜻이다. 파일 선택·게시 제출, 계정/본문/
자동화 연결 확인과 구분해 화면에 표시한다. 제휴 상품이 없는 콘텐츠의 별도 게시
정책과 예약 게시 기능도 이번에 임의로 추가하지 않았다.

메인 8775의 새 백엔드 적용은 제작 유휴 시점에 별도로 필요하다. 새 기능은 현재
`http://127.0.0.1:3235/monetization.html`에서 사용할 수 있다.
