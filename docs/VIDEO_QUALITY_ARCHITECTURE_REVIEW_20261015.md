## 판단

기존 개선은 실제 운영 장애를 상당 부분 정확히 진단했다. 검색 근거 검증, 현재 브라우저 접근 상태 확인, 중복 요청 방지, 실제 산출물과 검수의 연결, 표지와 본문 마스크 경로 통합, DB 경량화는 유지할 가치가 있다. 그러나 이 개선만으로 영상 품질 문제가 해결됐다고 판단하기는 어렵다.

핵심 결함은 네 가지다. 첫째, 수정한 마스크 시간축에도 반올림 때문에 한 프레임 지연이 남아 있다. 둘째, 검수는 이 프레임을 보지 않고도 통과할 수 있다. 셋째, 소스의 사용 가능 판정과 편집 선택이 제품의 매력을 보여주는 완성도까지 평가하지 않는다. 넷째, 부분 재편집은 기존 컷을 과도하게 고정해 전체 흐름과 반복을 개선하기 어렵다. 별도로 DB 복구에는 성공 상태를 잘못 반환하는 정합성 결함이 있다.

따라서 우선순위는 **정확한 마스크와 이를 잡는 검수 → 소스 표현 품질과 편집 구성 → 일반 복구와 검색 품질 보강**이다. DB의 허위 완료 반환은 영상 개선과 별개로 먼저 차단해야 한다. 수집량 확대, 더 강한 블러, 테스트 개수 증가만을 해결책으로 삼지 않는다.

## 실제 영상 품질을 낮추는 원인

### 마스크 경계가 한 프레임 늦는다

`auto_capcut/core/studio_render.py`는 ffprobe의 `best_effort_timestamp_time`을 float로 읽는다. `studio_masks.py:77`의 `preview_filter`는 이 값을 활성 구간 경계로 쓰고 `epsilon=1e-7`을 뺀다. ffprobe 출력은 소수점 여섯 자리여서 실제 PTS보다 최대 약 0.5마이크로초 늦게 반올림될 수 있다. epsilon이 이 오차보다 작다.

손난로 frame 179의 정확한 시각은 5.966666666667초인데 LUT는 5.966667초다. 활성 조건은 5.9666669초부터이므로 frame 179에서 false, frame 180에서 true다. 같은 경계에서 이전 마스크는 한 프레임 더 남는다. 명목 프레임을 실제 시간축으로 옮긴 기존 수정의 취지는 맞지만, 실제 시각을 반올림한 다음 비교하면서 오류를 다시 도입했다.

| 손난로 프레임 번호 | 최종 영상 시각 | 실제 관찰 |
|---:|---:|---|
| 179 | 5.966667초 | 이전 보라색 제품 컷의 마스크 위치가 남고 새 컷의 원본 자막 노출. 180에서 정상 가림. |
| 361 | 12.033333초 | 웹 화면 상단·하단 원본 문구 노출. 362에서 여러 블러 영역 적용. |
| 412 | 13.733333초 | 이전 웹 화면의 마스크가 새 제품 컷에 남아 있고 원본 자막 노출. 413에서 정상 위치로 변경. |

번호는 0부터 센 decoded frame ordinal이다. 후반 컷의 마스크 이전 concat 시각과 최종 CFR 시각은 다르므로 최종 MP4 시각을 마스크 입력 시각으로 대입하면 안 된다. 해당 차이까지 `mask-clock-audit.json`으로 분리했다. 수학적으로 늦은 활성 경계는 20개 중 6개였고, 그중 위 세 곳에서 눈에 보이는 자막 누출을 확인했다. 모든 수학적 지연이 반드시 읽을 수 있는 자막 누출로 이어지는 것은 아니다.

사과 완료본에서도 frame 481의 16.033333초에 상단·하단 원본 문구가 노출되고 다음 프레임에서 가려진다. 이 영상 전체의 원인을 하나로 단정하지는 않지만, 공통 렌더 경계 문제의 추가 회귀 자료로 사용한다.

### 현재 QA는 경계와 시간적 완성도를 충분히 검사하지 않는다

`daily_quality.py:394`는 각 beat의 12%, 50%, 88% 지점을 추출한다. 한 컷이 1초면 첫 샘플은 시작 후 120ms이므로 33~67ms의 노출을 놓친다. 전체 영상도 12개의 축소 이미지로 본다. 샘플에 없는 사건은 모델 성능을 높여도 판단할 수 없다.

반복 지표는 모델 검토 뒤에 계산돼 advisory로 붙는다(`daily_quality.py:426`). 반복량만으로 일괄 탈락시키지 않는 정책은 맞다. 그러나 그 수치가 가리키는 원본 구간 쌍을 실제 비교하고, 반복의 편집상 이유를 확인하는 필수 경로가 없다. `visual_repeat_detection_complete=false`, `audio_listened=false`인 결과도 `passed=true`다. `font_first_frame_voice_verified=true`도 청감 검수 완료처럼 읽힐 여지가 있다.

### 블러가 원문을 가리면서 제품의 매력도 함께 가린다

`source_mask_review.py:211`의 `propose_masks`는 샘플에서 발견한 각 OCR 영역을 해당 검토 구간 전체에 적용한다. 움직이는 문자나 길이가 바뀌는 자막은 서로 다른 사각형으로 쌓인다. 손난로에는 같은 높이의 여러 블러 띠가 동시에 있고, 스팀청소기는 화면 상단에 큰 중첩 블러가 반복된다.

이 방식은 문자 발견 누락에도 취약하면서 화면을 필요 이상 가릴 수 있다. 마스크 강도만 낮추거나 무조건 하나의 큰 사각형으로 합치면 각각 문자 재노출·과잉 가림이 생긴다. 문자 영역의 실제 등장 구간과 움직임, 제품과의 겹침을 함께 관리해야 한다.

### 편집 가능한 소스와 보기 좋은 소스가 구분되지 않는다

손난로 최종 사용 소스 3개는 모두 360×640이다. 1080×1920 출력은 가로·세로 각각 3배 확대이며 디테일을 복원하지 못한다. 12.033~13.733초 구간에는 웹/광고 화면의 상하 여백과 여러 블러 영역이 그대로 들어가 제품 화면이 작아진다. 사과 도입부에도 검정·흰 여백을 포함한 재편집 소스가 여러 개 사용된다.

`source_presentation.py:96`은 제품과 동작의 식별 가능성 중심으로 `quality_usable`과 `action_preserved`를 판정한다. 식별 가능은 최소 조건이지 세로 쇼츠의 완성도 조건이 아니다. 해상도 숫자만으로 배제하지 않는 기존 계약은 유지하면서, 실제 유효 화면 영역·제품 점유율·중첩 화면·블러 침범·디테일을 선택 비용에 반영해야 한다.

다운로더에는 `visible_quality`를 통한 현재 플레이어 화질 선택 경로가 있다. 사용한 360p 소스에 더 높은 화질이 실제 제공됐는지는 이번 검토에서 확인하지 않았다. “고화질을 받을 수 있는데 일부러 낮게 받았다”고 단정하지 않는다.

### 보유 수량이 최종 다양성으로 이어지지 않는다

손난로는 편집 가능 16개, 사용 가능 136.55초를 확보했지만 실제 사용은 3개다. `source_policy.py`의 총 길이 1.25배·core 4초 기준은 최소 제작 가능성을 설명할 뿐, 필요한 여러 기능과 구도를 균형 있게 편집할 수 있음을 보장하지 않는다. 스팀청소기는 2개만으로 길이 기준을 만족해 수집 목표가 충족된다.

손난로 최종 `semantic-plan.json`에는 beat별 4~6개 옵션, 전체 6개 소스가 존재했다. 그러나 `select-shots-request.json`에서는 20개 beat 모두 옵션 1개이고 19개가 이미 고정됐다. `scene_requirements.constrain_plan`의 기존 컷 보존과 anchor 고정 구조가 선택 공간을 제한한다. 최종 결과의 단일 옵션은 단순한 모델 후보 생성 실패로 해석하면 안 된다.

`studio_diversity.complete_allocation`은 제한된 상태 수에서 첫 무중복 배치를 찾으며, 실패하면 탐욕 선택으로 돌아간다. 최적 시청 경험을 찾는 목적 함수가 아니고, 탐색 한도와 실제 해 없음도 같은 `None`이다. 최종 호출에 후보가 하나뿐이면 어떤 선택기도 다른 소스로 바꿀 수 없다. 앞선 재편집에서 새 소스를 얻고도 기존 구성의 대부분을 그대로 유지한 것이 이번 사례의 직접적인 병목이다.

3개 원본 자체를 불합격 사유로 삼아서는 안 된다. 중요한 것은 실제 새로운 구도·기능·동작의 수, 같은 순간 재사용, 순서와 리듬이다. 다른 업로드에 재등장한 같은 영상은 SHA만 다른 경우 현재 지표에서 중복으로 잡히지 않는다.

### 자막 조각과 영상 컷이 묶여 동작이 잘린다

`studio_timeline.py:217`은 자막 cue 하나마다 beat를 만들고, 다음 cue 시작을 영상 컷 경계로 사용한다. 손난로는 16.8초에 20개의 렌더 구간이며 0.5초 미만 구간이 3개다. 같은 소스 내부의 연속 구간도 있어 이를 모두 눈에 보이는 전환 20회로 계산해서는 안 된다. 다만 “꺼냈거든요”, “알았는데” 같은 짧은 말 조각이 다른 화면 전환을 만들 수 있는 구조다.

자막 읽기 단위와 시각적 행동 단위를 분리해야 한다. 특히 소스 자체가 이미 여러 컷을 이어 붙인 편집본이면 새 컷 시작 직후 원본 내부 컷이 한 번 더 발생할 수 있다. 스팀청소기 frame 38→39처럼 한 프레임 후 화면이 다시 바뀌는 사례는 이러한 잔여 구간도 점검해야 함을 보여준다. 이것을 모두 마스크 지연으로 분류하지 않는다.

사과는 `frozen_beats`가 5번·16번에 기록돼 있다. 실제 선택 소스 길이와 출력 길이의 부족분은 각각 약 0.293초와 0.060초이고, 렌더러는 마지막 프레임 복제로 채운다. 두 구간의 영향을 동일하게 과장하지 말고, 특히 약 9프레임의 정지가 동작 도중에 생기는지 확인한다. “freeze가 있다”는 지표와 의도된 디테일 정지의 편집적 판단을 구분한다.

## 저장 복구에서 발견한 별도 결함

`hotpost/writing/jobs.py:92`의 `_recover_durable_result`는 `get()`에서 호출돼 조회 중 DB 상태를 변경한다. 격리된 임시 DB에서 아래 세 반례를 실행했다.

| 반례 | 현재 결과 | 문제 |
|---|---|---|
| failed job에 result.json만 있고 CLI 완료 영수증 없음 | completed로 변경 | 빈 receipt 목록도 검증을 통과한다. request/result SHA와 call identity도 확인하지 않는다. |
| 복구 UPDATE에 database is locked 주입 | get은 completed, DB는 failed | 저장 예외를 무시한 뒤 메모리 상태만 completed로 바꾼다. 후속 단계가 내구 저장되지 않은 성공을 믿을 수 있다. |
| 원 payload와 다른 비어 있지 않은 image 파일을 배치한 뒤 compact | 복원 payload가 원본과 다름 | 파일 존재와 크기만 검사해 원본 Base64를 제거한다. SHA 또는 원 바이트 동일성 검사가 없다. |

이는 기존 운영 데이터가 실제로 변조됐다는 주장이 아니다. 현재 코드가 잘못된 입력·저장 실패에 대해 지켜야 할 불변성을 지키지 못한다는 재현 결과다.

`migrate_writing_jobs_sqlite.py`는 worker.lock으로 worker를 막지만 일반 create/get/update 호출은 같은 락을 요구하지 않는다. 확인한 ID별로 복원 해시를 검증하지 않고 `UPDATE jobs SET payload=NULL WHERE payload IS NOT NULL`을 실행한다. 스크립트 안에는 백업/복원 절차도 없다. 현재 이관된 DB를 다시 migration하지 말고, 우선 복제 fixture에서 안전성을 보강한다.

## Sol 구현 순서와 인수 조건

### 작업 1 정확한 마스크 시간축과 경계 회귀

수정 중심은 외부 렌더 저장소의 `studio_masks.py`, `studio_render.py`, 관련 mask 테스트와 Hotpost의 `mask_application_evidence.py`다.

1. ffprobe에서 integer PTS와 rational time_base를 보관한다. 사람이 읽는 `*_time` 소수 문자열을 판정의 기준으로 쓰지 않는다.
2. 승인된 마스크 구간을 먼저 출력 프레임의 반열린 범위 `[start_frame, end_frame)`에 결속한다. 이후 해당 입력 프레임열에 정확히 적용한다. 소스 승인 범위나 제품 컷을 한 프레임 늘리는 수정은 하지 않는다.
3. 기존 시간 기반 overlay를 유지하는 최소 수정이라면, 인접한 정확한 PTS 사이의 중간값을 활성 임계값으로 사용해 목표 프레임 집합이 정확히 같도록 한다. float 출력 오차가 가장 가까운 프레임까지 거리보다 작음을 검증한다. 전체 파이프라인을 명시적 CFR로 정규화하는 대안은 원본→출력 프레임 대응과 드롭/복제까지 입증한 뒤 선택한다. 과거 문제가 있던 각 overlay의 `n`으로 단순 회귀하지 않는다.
4. cover frame 0 제외, VFR 입력, 29.97/30/60fps 입력, 소수 seek, concat의 비균일 PTS, 여러 겹 마스크, start/end 동시 전환을 테스트한다. 30fps의 1/3·2/3 소수 경계를 반드시 포함한다.
5. 마스크 이전 입력에서 각 프레임에 기대 영역을 직접 적용하는 별도 기준 결과와 출력 픽셀을 비교한다. production graph의 같은 시각 계산을 테스트 정답으로 재사용하지 않는다.

합격 조건은 fixture의 모든 지정 프레임에서 잘못된 이전 마스크·늦은 새 마스크 0건, 실제 손난로 179/361/412 및 사과 481 경계의 원본 문자 누출 0건이다. 대본·음성·선택 source interval·표지의 의미를 바꾸지 않는다. 인코더 압축 오차 허용 범위와 문자 판독 검사를 구분한다.

### 작업 2 최종 검수를 기술 검수와 편집 검수로 분리

수정 중심은 `daily_quality.py`, `daily_quality_scope.py`, `product_appeal_review.py`, 결과 상태와 UI 표시다.

1. 기술 검수는 전체 decode, 프레임 대응, 마스크 경계, 예상 밖 freeze/black frame, 오디오 결속을 검사한다. 모든 컷·마스크 시작/끝 전후 최소 2프레임을 반드시 포함한다.
2. 문자 변화와 내부 컷은 선택 구간 전체를 순차 스캔한다. OCR 결과만으로 pass를 결정하지 않는다. 마스크 기대 영역과 실제 픽셀의 불일치는 기술 실패, 검출하지 못한 새 문자는 추가 검토 대상으로 분리한다.
3. 편집 검수는 전체 흐름, 제품 매력, 기능 전달, 반복, 화면 점유율, 블러 침범, 원본 내부 전환을 본다. 반복 지표와 재사용 구간 쌍을 검토 입력에 먼저 넣는다. 정지 이미지로 움직임이 필요한 결론을 내리지 않는다.
4. 결과에 `technical_pass`, `editorial_pass`, `audio_timing_pass`, `audio_listened`, `unchecked_scopes`를 구분한다. 이는 제안 필드이며 기존 저장 완료본은 읽기 호환성을 유지한다. 새 완료본은 정책상 필수 검수가 전부 pass일 때만 quality_verified가 된다. 청감 미검토를 음색 검증으로 표시하지 않는다.
5. 불확실한 검토와 명시적 결함을 구분해 필요한 구간만 추가 검토한다. 모든 프레임을 모델에 반복 전송하지 않는다.

합격 조건은 “기존 QA가 pass한 실제 누출 fixture”를 새 QA가 실패시키는 것, 정상 fixture는 통과하는 것, 검사하지 않은 범위를 완료로 표시하지 않는 것이다. 숫자만으로 반복을 무조건 불합격시키는 정책으로 바꾸지 않는다.

### 작업 3 소스의 화면 품질과 마스크 비용 평가

수정 중심은 `source_presentation.py`, `source_mask_review.py`, `source_overlay_review.py`, `source_segments.py`, `youtube_download.py`, `scene_analysis.py`다.

1. 실제 소스의 영상 영역 bbox, 레터박스·필러박스, 화면 안에 들어간 다른 화면, 제품 점유율, upscaling, 압축 손상, 블러 면적과 제품 겹침을 기록한다. 임계값만으로 자동 거절하지 말고 제품 식별과 감상 품질을 함께 평가한다.
2. 깨끗하고 제품이 크게 보이는 후보를 우선한다. 같은 source의 더 높은 화질이 현재 허용 세션에서 확인되면 그 변형을 검토하되, 접근 오류를 우회하거나 미확인 고화질 URL을 추정하지 않는다. 새 파일 SHA에 필요한 시각 검토를 다시 연결한다.
3. 화면 속 화면은 실제 영상 영역을 찾아 크롭 후보를 만든다. 크롭으로 동작이 잘리거나 과도하게 확대되면 다른 소스를 선택한다. 변환한 기하에 마스크 좌표와 시각 근거를 다시 결속한다.
4. OCR 사각형을 4초 전체에 쌓는 대신 문자 등장·퇴장·이동 구간을 추적한다. 선택한 실제 사용 구간에서 정밀화해 비용을 제한한다. 제품 로고·인쇄 문자와 원작 삽입 자막도 구분한다.
5. 새 마스크는 실제 픽셀 검토를 거친다. 겹치는 영역 병합은 동일한 가림·제품 보존을 입증할 때만 한다. 블러를 약하게 하거나 전체 화면을 가려 통과시키지 않는다.

합격 조건은 손난로 12.033~13.733초와 사과 도입의 큰 여백 컷을 재검토 대상으로 식별하고, 블러가 제품의 핵심 구조를 침범한 경우 선택 비용에 반영하는 것이다. 360p라는 이유만으로 기존 영상을 일괄 폐기하지 않는다.

### 작업 4 전역 편집 구성과 부분 복구 범위 개선

수정 중심은 `scene_analysis.py`, `scene_requirements.py`, `studio_runtime/editing.py`, `daily_quality.py`, 외부 `studio_diversity.py`와 `studio_timeline.py`다.

1. 대본을 제품의 시각적 역할로 묶는다. 예를 들면 손난로의 외관, 손에 쥐는 사용, 거울, 조명, 충전, 마무리다. 모든 문장의 사건을 똑같이 재현하는 요구를 추가하지 않는다. 역할별로 실제 구간과 대체 후보를 연결한다.
2. 자막 cue와 영상 cut을 별도 구조로 둔다. 여러 cue를 한 동작 컷 위에 표시할 수 있게 하며, cut은 기능·행동·구도의 변화와 적정 노출 길이를 기준으로 정한다. 기존 cue ID와 캡션 편집 호환을 위한 mapping을 제공한다.
3. 대본 적합성과 필수 native frame은 hard constraint로 유지한다. 반복 원본 시간, 같은 시각 모티프, 과도한 동일 소스 점유, 제품을 가리는 블러, 화면 속 화면, 잘린 동작은 최적화 비용으로 둔다. 원본 개수 최대화를 목적 함수로 삼지 않는다.
4. 선택 결과에는 후보가 탈락·고정된 이유와 단계별 후보 수를 남긴다. semantic 후보 → constraint 후 후보 → allocator 입력 → 최종 컷을 비교할 수 있어야 한다. 완전 배치 실패와 탐색 예산 소진을 별도 결과로 반환한다.
5. 반복 결함은 지적된 beat 하나가 아니라 겹치는 원본 구간·같은 시각 모티프를 공유하는 컷 묶음을 수정 범위로 삼는다. 손난로의 13/14/18/20 재사용 구간이 회귀 사례다. 영향 밖의 대본·음성·무관한 컷은 보존한다.
6. 모든 선택과 native anchor 검증을 마친 뒤에 렌더 계획을 고정한다. 고정은 재선택 방지를 위한 최종 단계여야 한다. 재편집 시작부터 과거 옵션 하나로 줄여 전역 개선을 막지 않는다. 렌더러는 확정 계획을 검증·실행하고 몰래 재선택하지 않는 방향으로 책임을 정리한다.

합격 조건은 기존 16개 ready pool로 가능한 대안을 먼저 비교하는 것이다. 현재 영상의 동일 원본 시간 재사용 비율은 약 21.8%다. 원칙적으로 불필요한 동일 순간 재사용 0을 목표로 하고, 의도된 회상·마무리 반복은 실제 편집상 이유를 남긴다. 낮은 반복량을 얻으려고 무관한 소스·부품·반대 동작을 넣으면 실패다. 3개만 써도 새 기능과 구도를 충분히 보여주면 허용하며, 10개를 써도 흐름이 나쁘면 통과시키지 않는다.

### 작업 5 필요한 소스만 보충하는 수집 목표

수정 중심은 `source_policy.py`, `source_coverage.py`, `scene_requirements.py`, `source_planning.py`, `source_queries.py`, `studio_sources.py`다.

1. 최소 총 분량과 별개로 편집 역할별 사용할 수 있는 구간·대체 후보·시각 품질 부족을 저장한다. 충분한 재고가 있는데 최종 편집이 단조로운 경우를 수집 부족과 분리한다.
2. 실제 보유 파일에서 장면 경계와 필요한 행동 주변을 찾아 좁은 구간으로 검토한다. 처음·중간·끝 4초만으로 전체 파일의 쓸모를 판단하지 않는다.
3. 기존 자료로 해결 불가한 역할만 검색한다. 총 10개·TikTok 5개를 일괄 강제하지 않는다. 실제 접근 대기와 콘텐츠 부족도 분리한다.
4. 동적 명사를 프로세스 전역 목록에 무기한 추가하는 대신 reference SHA·인용·subject ID·허용 번역을 담은 작업별 검색 계약을 전달한다. worker는 근거 없는 provider query 문자열 자체를 승인 근거로 등록하지 않는다.
5. 액션 검색은 현재 중심 대상 또는 명시적으로 허용한 부품과 연결됐는지 확인한다. “아무 알려진 명사가 있다”는 조건으로 중심 대상 검사를 건너뛰지 않는다. 언어별 번역도 같은 대상으로 연결한다.

합격 조건은 미등록 신상품이 근거 있는 짧은 검색어로 검색 가능하고, 관련 없는 조명·부품이 중심 제품으로 대체되지 않는 것이다. 다른 작업에서 동적 명사를 등록한 순서에 따라 현재 작업 결과가 달라지지 않아야 한다.

### 작업 6 내구 저장과 기술 실패 복구

수정 중심은 `writing/jobs.py`, `migrate_writing_jobs_sqlite.py`, `quality_progress.py`, `daily_quality.py`, `studio_workflow.py`다. 이 중 허위 완료 반환 차단은 작업 1과 함께 최우선으로 처리한다.

1. `get()`은 조회로 유지하고, 복구는 명시적인 worker 단계에서 수행한다. 성공 artifact의 존재와 DB commit 완료를 별도 상태로 표현한다.
2. 요청 SHA, job/kind, 실제 실행 call ID, terminal success, 결과 SHA, 소유권과 취소 상태를 연결한 영수증으로만 저장을 복구한다. 영수증 0개를 통과시키지 않는다. 여러 실행 중 실패 이력이 있더라도 현재 결과에 해당하는 정확한 성공 실행을 판단한다.
3. DB commit 실패 시 completed를 반환하지 않는다. 같은 결과로 저장만 재시도하고 모델은 재호출하지 않는다. 실패 이력은 지우지 않고 append한다. 최종 update에는 현재 상태·소유·cancel 조건을 적용해 늦은 복구가 사용자 취소를 덮지 않게 한다.
4. 미디어 외부화 전에 Base64 decode 바이트와 외부 파일 SHA가 같음을 확인한다. `_external_file`에는 상대 경로, 크기, SHA를 보관하고 읽을 때 검증한다. 파일 없음·변조는 불완전 자료이지 정상 payload가 아니다.
5. 마이그레이션은 백업, 모든 writer의 진입을 막는 maintenance 경계, 행별 복원 해시 검사, 검증된 ID만 NULL 전환, 중단 후 재개·롤백을 갖춘다. 원 DB를 무검증 일괄 변경하지 않는다.
6. 재개 판단에는 오류 타입과 실패 단계, 이미 존재하는 완료 artifact, 동일 실패 방법 여부를 사용한다. retry suffix는 큐 충돌 해결 수단이고 성공의 근거나 무제한 재시도 허가는 아니다.

합격 조건은 이번 세 저장 반례를 모두 차단하고, 결과 파일 저장 후 DB lock/crash를 주입해도 모델 실행 1회·복구 후 DB와 API 상태 일치·원래 실패 이력 보존이 성립하는 것이다. 취소와 복구의 경쟁, 다른 요청의 result, missing media, 같은 ID의 동시 create, 이관 중 신규 writer도 fixture로 검증한다.

## 검증 결과와 구현 종료 조건

이번 검토에서 기존 보고서의 명령을 재실행해 Hotpost 143개 테스트가 2.36초에 통과했다. 외부 렌더의 `test_studio_masks.py`, `test_studio_diversity.py`, `test_studio_timeline.py`는 51개가 16.03초에 통과했다. 따라서 기존 테스트가 틀렸다고 일반화할 수는 없지만, 이번 프레임 및 저장 반례를 보장하는 테스트가 없다는 점은 분명하다.

Sol은 작업별 작은 변경과 관련 회귀를 먼저 끝내고, 마지막에 네 기존 완료본을 기준 자료로 비교한다. 손난로·사과는 실제 누출과 편집 품질 실패 사례, 밥도그는 낮은 재사용과 기존 마스크 수정을 보존해야 할 사례, 스팀청소기는 두 원본 안의 여러 동작과 동일 업로드 반복을 구분할 사례다. 중국어·한국어·영어의 삽입 문자와 원본 내부 컷이 있는 별도 fixture도 포함한다. 네 사례를 모두 튜닝 자료로 쓴 뒤 독립 검증이라고 부르지 말고, 별도의 미사용 사례로 일반화를 확인한다.

완료 보고에는 코드 테스트 통과뿐 아니라 다음 결과가 필요하다.

- 지정된 실제 경계의 전후 프레임, 누출 수, 잘못된 마스크 잔류 수.
- 동일 음성·대본에서 새 편집이 제품을 더 잘 보여주는 이유와 전후 전체 흐름 비교.
- 실제 사용 원본·시각 모티프·재사용 구간·정지 구간·블러/여백 문제의 변화.
- 작업 6의 DB 및 파일 fault injection 결과와 모델 재호출 수.
- 확인하지 못한 청감·외부 고화질 제공 여부 등의 범위를 구체적으로 표시.

정책·데이터 구조 변경은 버전을 올려 새 실행부터 적용한다. 과거 완료본의 SHA와 계약을 맞추기 위해 기존 파일이나 영수증을 고치지 않는다. 캐시 무효화는 실제 입력·픽셀 변환·검토 정책 변경에 근거해야 하며, 코드 해시나 새 job 이름만으로 같은 실패 방법을 새 개선으로 인정하지 않는다.

## Sol에게 전달할 실행 지시

이 문서의 작업 1과 작업 6의 허위 완료 차단부터 구현하고, 작업 2로 실제 실패를 잡는 검수 경로를 만든 다음 작업 3·4·5 순으로 품질을 개선한다. 먼저 현재 diff와 `audit-manifest.json`의 검토 시점 SHA를 비교한다. 기존 변경을 덮어쓰거나 완료 task를 일괄 재개하지 않는다. 외부 렌더는 별도 저장소·가상환경·JSON 프로세스 경계를 유지한다. 최초 수정 영상은 기존 파일을 보존한 새 산출물로 만들고, 검증 결과와 계획 대비 남은 항목을 보고한다. 이번 요청은 분석·계획 작성이므로 이 문서 자체를 자동 운영 재개나 게시 권한으로 해석하지 않는다.
