## 1. 수집과 검토를 교대로 실행

### 원인

`hotpost/source_finder.py`의 후속 수집 조건은 `scene_duration`에서도 다운로드된 후보 수를 `source_max_downloads`와 비교한다. 이번에는 최초 15개 중 13개를 수신한 뒤, 정식 구간 검토 전에 새 9개 후보까지 처리했다. 반면 `hotpost/studio_sources.py`는 검토된 3개에서 24초를 확보하자 나머지 검토를 종료했다. 따라서 검토의 조기 종료 기능을 새로 만드는 것이 아니라 **그 판단을 다음 수신 묶음보다 앞에 배치**해야 한다.

중요한 제한: 최종 선택은 04·17·06이며 17은 추가 검색에서 얻은 후보다. 추가 검색 전체가 불필요했다거나 약 10분을 그대로 절약할 수 있었다고 확정할 수 없다. 최초 13개 중 나머지는 정식 사용 구간 미검토 상태여서, 그 자료만으로 동일 품질의 분량을 확보했을지도 미확인이다.

### 변경할 흐름

1. 원본과 결속된 제품 특징 검색 계획을 한 번 확정한다.
2. 현재 검색에서 얻은 후보 목록과 실제 소비한 페이지·커서·URL을 보존한다.
3. 우선순위가 높은 작은 묶음을 수신한다. 초기 묶음 크기 3은 실행 단위이며 합격 수량이나 전체 시도 상한이 아니다.
4. 수신 파일을 기존 글자·마스크·기능·세로 화질 검토 경로에 전달한다.
5. 기존 `source_goal`/`coverage_goal`로 중복을 제외한 사용 가능 분량과 핵심 장면을 계산한다.
6. 충족하면 수집을 완료한다. 부족하면 이미 발견했지만 아직 받지 않은 후보부터 다음 묶음으로 진행한다.
7. 보관 중인 후보가 부족할 때만, 확인된 부족 장면을 지원할 미사용 검색 범위를 연다.

기본 1.25배 분량·핵심 4초와 TikTok 수량의 선호 표시는 기존 정책을 따른다. 무관 소스, 미검토 파일, 같은 부모 구간의 중복 초수로 목표를 채우지 않는다. 부족한 경우에는 유효한 새 근거와 검색 범위가 있는 동안 계속 진행한다.

### 코드 경계와 복구

- `source_finder.py`: 검색·수신을 한 묶음씩 완료할 수 있는 경계와 남은 후보 목록을 반환한다. 20개는 보관 상한이며 자동 완료 목표로 사용하지 않는다.
- `studio_sources.py`: 수신 묶음과 기존 검토·분량 판정을 연결한다. 정책 판단은 이곳의 기존 함수 하나를 사용한다.
- `source_attempts.py`, 기존 worker/checkpoint: 발견 목록·소비 범위·파일 SHA·검토 SHA·다음 후보 위치를 현재 claim에 결속해 저장한다.
- 묶음마다 불변 manifest 스냅샷을 만들고 누적 목록은 별도 인덱스가 참조한다. 검토 후 manifest를 계속 덧써 기존 전체 파일 SHA 결속이 깨지는 문제를 피한다. 검토 재사용은 해당 파일·구간·정책·실제 프레임 SHA가 모두 일치할 때만 허용한다.
- 부분 묶음 저장을 전체 수집 완료로 표시하지 않는다. 재시작은 같은 작업의 남은 후보/구간부터 수행한다. 이전 정상 파일·실패·접근 제한은 보존한다.
- 검토 모델이 용량 대기이면 그 상태를 기록한다. 검토 결과가 없다는 이유로 후보 20개를 채우는 별도 수집 루프를 실행하지 않는다.
- 별도 Studio 소비자를 만들거나 Playwright 객체를 여러 스레드에서 공유하지 않는다. 기존 프로세스 경계와 브라우저 lease를 유지한다.

### 검증

- 첫 묶음으로 분량 충족: 이후 외부 검색·다운로드 요청 0회.
- 첫 묶음 부족: 남은 발견 후보를 먼저 사용하고, 소진 뒤에만 미사용 검색 범위 실행.
- 3개 수신했지만 전부 무관: 완료 처리 금지. 반대로 TikTok 3개여도 실제 분량·핵심을 충족하면 계속 수집하지 않음.
- 동일 구간 리포스트 3개: 중복 분량을 합산하지 않음. 같은 제품의 다른 유효 상태는 활용 가능.
- 묶음 중 사용자 중지·claim 교체·재시작: 파일과 검토는 보존하고 늦은 결과의 상태 수용 거부.
- 기존 정책의 구형 수량 모드는 별도로 보존한다.

관련 기존 검사: `test_source_quota_policy.py`, `test_source_coverage.py`, `test_parallel_sources.py`, `test_source_pause_history.py`, `test_deferred_download_review.py`, `test_source_expansion.py`.

## 2. 후속 검색도 같은 제품을 찾도록 제한

### 원인과 변경

`source_queries.tiktok_product_queries()`는 검토된 시각 명사구를 앞에 놓지만, 문자 근거의 넓은 명사도 뒤에 합친다. 이번에는 정밀한 나사형 슬라이더 검색 다음에 ‘지퍼’가 실제 제출돼 왕지퍼 후드집업이 수신됐다. 이는 문법적으로 짧은 명사구라도 제품 식별 범위가 달라질 수 있음을 보여준다.

최종 전송 직전에 모든 경로의 질의를 같은 기준으로 판정한다. 첫 검색·후속 검색·재개·대체 플랫폼에 동일한 제품 정체성을 전달한다.

- 제품의 중심 명사와 구별되는 구조를 기록한다. 이번에는 ‘교체용 지퍼 슬라이더’가 중심이며 나사형/개폐 구조는 실제 영상으로 확인된 특징이다.
- 색상 같은 부수 조건을 완화하는 것과 ‘교체 부품’을 ‘의류 지퍼 일반’으로 바꾸는 것을 구분한다.
- 승인된 언어별 동의어와 미사용 페이지·커서는 재사용한다. 부족하다고 임의의 새 문구를 계속 생성하지 않는다.
- 질의별 원본·관찰 프레임 SHA, 유지된 제품 특징, 완화한 조건과 이유를 기록한다. 새로운 특징·브랜드·소재는 기존과 같이 독립 근거가 필요하다.
- 넓은 질의만 남으면 자동으로 전송하지 않고 검색 범위 부족 상태를 남긴다. 이미 받은 후보 검토는 계속할 수 있다.
- 검색 카드의 제목·미리보기는 관련 후보의 우선순위에 사용한다. 미리보기가 불분명하다는 이유만으로 실제 관련 소스를 확정 탈락시키지 않는다.

`source_visual_queries.py`, `source_queries.py`, `source_planning.py`와 `source_finder.py`의 후속 검색 호출을 함께 변경한다. 이미 동작하는 canonical URL 중복 제거는 유지한다.

검증은 첫 검색뿐 아니라 후속·재개 시 실제 provider에 전달된 질의까지 확인한다. ‘지퍼’처럼 원문에 존재하는 명사도 교체 부품의 정체성을 잃으면 해당 계획의 자동 확장에 사용되지 않아야 한다. 시각 근거 없는 제품은 별도의 문자 근거 경로로 처리하며 시각 특징을 만들어 넣지 않는다.

## 3. 다운로드 실패를 설명할 수 있도록 기록하고 감시

### 확인된 원인과 미확인 원인

확인된 문제는 `source_attempts.transfer_diagnostics()`가 접근 상태 중심의 일부 키만 보존해 `direct_error`·미디어 통계·진전 기록을 버린다는 것이다. 첫 수신이 오래 걸린 정확한 호출은 아직 확정되지 않았다. `response.body()`나 동기 DOM 호출의 대기 가능성을 실제 원인으로 단정하지 않는다.

### 우선 구현할 진단

- 각 후보의 주 경로와 대체 경로를 별도 시도로 기록한다.
- 시작·첫 응답·마지막 유효 진전·종료 시각, 현재 단계, 요청 시도/미시도, 실패 유형을 보존한다.
- 선택한 항목과 결속된 미디어의 누적 고유 수신 범위·완전한 파일 조립 여부·마지막 재생 상태를 작은 구조화 값으로 보존한다.
- `direct_error`와 대체 경로 오류를 각각 보존한다. 대체 경로 오류가 주 경로의 원인을 가리지 않게 한다.
- 실행 중에는 현재 상태를 원자 checkpoint로 갱신하고, 최종 요약과 종료 이유를 별도 기록한다. 로그 갱신 자체를 유효 진전으로 세지 않는다.
- 허용 필드의 타입·길이를 검증한다. 쿠키·인증 헤더·서명된 CDN URL·원시 HTML/응답 본문은 기록하지 않는다. 필요하면 미디어 식별자는 해시로 저장한다.

### 무진전 처리

기존 단계별 무진전 감시를 유지하며 실제 선택 미디어의 새로운 바이트 범위나 완료된 처리가 진전인지 검사한다. 같은 바이트 재수신·광고·추천 영상·반복 재생·프로세스 생존은 진전으로 취급하지 않는다. 정상 수신이 증가하면 계속 실행한다.

진단으로 동기 Playwright 호출이 감시 실행을 막는 것이 확인되면, 해당 수신 루프를 이벤트와 감시가 함께 실행되는 비동기 방식으로 분리한다. 별도 스레드에서 같은 Playwright 객체를 호출하지 않는다. 취소는 해당 시도의 listener·수신 작업과 소유한 worker에 한정하며 사용자의 Chrome 창·로그인 세션을 종료하지 않는다. 늦은 결과는 현재 claim 검증 후에만 수용한다.

현재 CAPTCHA·로그인·429·HTTP 접근 거부는 기존 제한에 따른다. 대체 사이트 차단/휴식도 보존한다. 같은 실패 URL을 자동으로 다시 요청하지 않는다.

검증 반례: 고유 바이트가 계속 증가하는 긴 수신, 동일 Range 반복, 추천 영상만 수신, 첫 응답 없음, 본문 수신 중단, 주 경로 실패+대체 미시도, 동기 콜백 정체, 중지 후 늦은 완료, 민감 URL/헤더의 진단 유출. 관련 경로는 `tiktok_download.py`, `tikvideo_download.py`, `operation_progress.py`, `source_attempts.py`다.

## 4. 원고 3안과 TopPick 평가 계약 일치

`writing/variants.py`는 1·2안의 다른 심리 장치를 요구하지만 `studio_top_pick._choose_scored()`의 대체 평가 프롬프트는 원작 후킹·순서를 보존하고 심리 장치가 바뀌면 낮게 점수 주도록 명시한다. 이 모순을 제거한다.

- 후보마다 `variant_type`, 카테고리·편향, 원작 분석과 변경점을 평가 입력에 보존한다.
- 1·2안은 같은 심리 카테고리 안의 새로운 장치·갈등·전개로 평가한다. 3안만 원작 장치·전개 유지와 의미 있는 표면 변경을 평가한다.
- 공통 검토는 실제 제품 매력, 자연스러운 발화, 사실·복사 여부를 본다. 이야기 설정 변경을 제품 사실 추가와 혼동하지 않는다.
- ‘나사가 보인다’ 같은 시각 사실은 현재 원본·실제 프레임 SHA에 연결된 집필 근거를 재사용한다. 글에 그 단어가 없다는 이유만으로 근거 없다고 판단하지 않는다. 가격·정확한 수치·소재 같은 미관찰 사실은 여전히 추가하지 않는다.
- 기존 유효한 편집 평가를 재사용하는 경로와 대체 평가 경로 모두 같은 계약을 적용한다. 정책 버전을 올리고 옛 평가 기록은 보존한다.
- advisory 상태를 유지한다. 취향 의견이나 평가 서비스 대기를 새 제작 승인 절차로 바꾸지 않는다.

검증: 정상 유형전환 2안과 표면 치환 1안을 동일 기준으로 구분하며, 구조가 실제 보이는 사례와 추정만 있는 사례를 대조한다. 소스 확보 수·편집 편의가 원고 순위에 영향을 주지 않아야 한다. `test_writing_variants.py`, `test_internal_writing.py`, `test_top_pick_claims.py`를 확장한다.

## 5. 썸네일 자연스러움은 렌더 전에 확인

`thumbnail_copy.py`에는 자연스러운 한국어 지시가 이미 있지만 로컬 `review_copy()`는 일부 일반적인 궁금증 표현만 검사한다. ‘옷 한 벌을 예산에?’ 같은 의미가 끊기는 문장을 판정할 수 없다.

기존 집필 3안의 검토 입력에 두 줄을 합친 문구와 제품·본문·실제 참조 이미지를 함께 넣는다. 추가 검토 루프를 따로 계속 만드는 대신 기존 안별 검토/보완 결과에 아래 항목을 저장한다.

- 문장의 생략된 부분을 시청자가 자연스럽게 이해할 수 있는가.
- 두 줄을 이어 읽었을 때 상황과 질문이 성립하는가.
- 제품·시청자 이득 또는 갈등이 구체적인가.
- 본문이 질문에 답하며 미확인 가격·인기·기능을 추가하지 않는가.
- 선택된 이미지와 결합했을 때도 같은 의미인가.

명사형·짧은 구어체·질문을 일괄 금지하지 않는다. 특정 실패 문구 하나의 금칙어 목록으로 대신하지 않는다. 근거 있는 어색함은 해당 문구만 보완하고 이전/수정 문구와 이유를 저장한다. 일반 내용 의견은 advisory로 유지하고 재질문으로 통과를 얻는 반복은 막는다. 실제 첫 프레임 최종 검토도 계속 수행한다.

회귀에는 이번 실패 문구, 정상적인 짧은 생략문, 질문 없는 제목, 기존 ‘제품명+왜’ 반복, 미확인 가격 약속, 글자는 자연스럽지만 이미지와 무관한 사례를 포함한다. 생성·선택·표지 검토가 동일 정책·선택 문구 SHA를 사용해야 한다.

## 6. 표지 수정의 본문 보존 경로 연결

`studio_thumbnail.py`에는 첫 프레임을 바꾸고 본문 디코드 프레임·음성을 비교하는 기능이 이미 있다. 다만 일반 썸네일 문서 편집 경로를 그대로 호출하면 `cover_spec.lines`, CapCut 표지 소재와 정상 최종 QA 계약이 일치하는지 별도로 해결해야 한다.

정상 품질 보완에서 변경 범위가 표지 문구뿐인 경우 이 경로를 연결한다. 이전 본문 MP4를 원본으로 삼고 새 표지 한 프레임만 만든다. 선택된 실제 배경·마스크·얼굴 없음 근거, 새 문구·폰트·배치, plan과 CapCut 표지 트랙도 함께 갱신한다.

완료 조건은 프레임 수·시각·길이 동일, 첫 프레임을 제외한 디코드 프레임 해시 동일, 음성 해시 동일, 본문 계획 동일이다. 그 뒤 새 파일/계획 SHA에 결속한 정상 최종 QA와 공유 검사를 거친다. 전제 불일치이면 무손실 표지 교체 완료로 표시하지 않고 기존 정상 렌더 경로를 사용한다. 기존 완성본을 덮어쓰지 않는다.

초기 구현에서는 최종 QA를 생략하지 않는다. 본문 검토 재사용은 실제 본문 픽셀·오디오·계약 동일성에 대한 별도 검증이 준비된 뒤의 후속 최적화다.

## 7. 승인 음성·톤 관리와 시간 측정

이번 영상은 Seed 13/개인 참조/전체 원고 1회 합성이 실제 기록과 일치한다. 다만 VoiceBench `runner.py`에는 기본 Seed와 다른 QA 재시도 Seed를 사용하는 경로가 남아 있다. 승인 Seed 고정 제작은 요청 기본값뿐 아니라 재시도 계획에도 같은 정책을 연결해야 한다. 다른 영상의 Seed 10 예외를 새 영상에 적용하지 않는다.

동일 Seed·동일 입력으로 같은 실패 음성을 다시 만드는 것은 개선으로 세지 않는다. 재시도는 실제로 달라진 유효 근거가 있어야 하며, 승인된 음성 조건으로 품질을 만족하지 못하면 그 상태와 원인을 보존한다. 다른 Seed를 자동 선택해 완료 처리하지 않는다. VoiceBench와 클라이언트의 HTTP 경계는 유지한다.

실제 Seed·참조 SHA·엔진 파라미터, 원문/발음 치환, 전체 합성 여부, 무음 정리와 속도를 한 영수증에서 구분한다. 설정 일치와 승인 거울 영상 같은 청감이라는 판단을 분리한다. 청감은 승인 음성과 새 음성을 같은 재생 조건에서 비교한 근거로 판단하고 CTA·자막은 최종 오디오에서 확인한다.

시간은 접수 대기, 실제 실행, 요청 간격/접근 대기, 모델 용량 대기, 실패, 품질 보완, 공유 확인으로 나눈다. 병행 단계는 총시간에 중복 합산하지 않는다. 서비스·브라우저 대기를 콘텐츠 실패로 표시하지 않는다.

## 적용·검증 순서

1. **진단 보존과 검색 범위 판정**을 먼저 추가한다. 다운로드 장기 대기의 원인과 실제 요청을 잃지 않도록 한다.
2. **묶음 수신→검토→분량 판정**을 정상 큐·checkpoint에 연결한다. 저장·중지·복구·동일 실패 방지를 우선 검증한다.
3. **TopPick과 썸네일 집필 검토**를 공통 3안 계약에 맞춘다. Seed 정책도 실제 합성 재시도까지 연결한다.
4. **표지 한 프레임 수정**을 정상 품질 보완에 연결한다.
5. 관련 격리 검사 통과 후 유휴 운영 프로세스의 실제 코드 로딩을 확인한다. 기존 Chrome·VoiceBench 세션과 원본·완성본·작업 이력을 보존한다.

현재 남아 있는 미커밋 변경을 기준선으로 보관하고 이번 변경만 구분한다. 운영 활성 작업을 코드 변경만으로 재개하지 않는다. 후속 신규 실영상은 승인된 다음 선정 범위에서 수행하며, 현재 완료된 상위 3개를 다시 만들거나 하위 순위를 임의 대체하지 않는다.

### 효과 검증

- 먼저 이번 24개 후보 목록·파일 SHA·실제 검토 영수증을 별도 복제 자료로 사용해 요청·분량 판정 순서를 재현한다. 기존 미검토 후보를 승인된 자료로 간주하지 않는다. 원본 운영 상태와 과거 검수는 수정하지 않는다.
- 동일 입력의 모의 외부 응답 검사로 과수집·중복·중지·복구를 검증한다. 이는 실제 제품 품질이나 네트워크 절약 실측과 구분한다.
- 후속 실제 영상은 기존 준비자료 재사용 여부, 음성 길이, 제품, 실제 검색·수신·모델 호출 수와 품질 보완 수를 함께 기록한다.
- 핵심 지표는 ‘처음 분량 충족 이후 불필요한 요청 0회’, ‘제품 정체성을 잃은 자동 후속 질의 0회’, ‘같은 콘텐츠 실패 입력의 무의미한 반복 0회’, 최종 품질 통과·보존 조건이다. 기존 요청 ID의 상태 조회와 정상 전송 재시도는 이 실패 반복과 구분한다.
- 시간 개선은 같은 경계의 총시간과 소스 단계 시간을 함께 보고한다. 여러 신규 사례의 중앙값과 범위를 기록하며 제품이 다른 과거 92분·55분 사례만으로 코드의 인과 효과를 주장하지 않는다.

추가 수집 10분 전체의 절약이나 모든 영상을 특정 시간 내 완성한다는 수치는 현재 근거로 보장하지 않는다. 가장 먼저 검증할 가설은 **충분한 소스가 확보된 뒤에도 이어지는 수신과, 제품 범위를 잃은 후속 검색을 줄여 품질을 유지하면서 제작시간을 줄일 수 있는가**다.
