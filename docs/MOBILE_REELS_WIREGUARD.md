# WireGuard를 통한 Android 릴스 게시 경로

현재 PC → 기존 WireGuard VPN → 휴대폰 ADB → Instagram/Edits의 보이는 화면 순서다. 다른 PC나 기존 제작실 실행기를 거치지 않는다. 구현은 로컬 CLI이며 공개 Cloudflare 웹서버에 폰 제어/페어링/임의 셸 API를 추가하지 않았다. 단순 서버 시작이나 문서 읽기로 폰 작업이 재개되지 않는다.

## 현재 확인한 것과 남은 것

- Windows PC의 기존 WireGuard 경로 활성은 확인했다. PC/폰의 실제 IP와 포트는 각 PC의 Git 제외 로컬 설정과 기록에서 관리한다.
- `requirements-mobile.txt`의 uiautomator2 3.7.0/adbutils 2.12.0 설치, 포함된 Windows adb 실행 확인. 전역 PATH/방화벽/VPN 설정 변경 없음.
- 초기 기존 완성본 시험은 H.264 High/4.1, yuv420p, AAC였으며 16.633초/499프레임과 화면 크기를 유지했다. 이후 사용자 확정 규칙에 맞춰 현재 모바일 전달 경로도 공통 `encode_delivery`의 **H.264 Main@4.0/yuv420p/AAC-LC/+faststart**로 통합했다. 원래 최종본은 수정하지 않는다.
- 2026-10-26 실제 폰(Galaxy SM-S948N, Android 17)에서 WireGuard 경유 무선 디버깅 페어링·`connect`·Instagram/Edits 설치 확인·Instagram 홈 화면 캡처까지 확인했다. 무선 디버깅 연결/페어링 포트가 VPN 주소로 접속을 받았다. 계정 확인·영상 전송·작성기·릴스 게시 검증은 아직 하지 않았다. `doctor`는 필수 연결 정보가 없으면 `needs_phone_details`로 표시한다.
- 같은 폰에서 uiautomator2 `app_current()`가 포커스 없는 배경 앱(YouTube)을 반환했다. 현재 앱은 `dumpsys window`의 `mCurrentFocus`(없으면 `mFocusedApp`)로 판정한다.
- Edits의 영상 수신/Instagram 넘기기, 앱 버전별 본문/계정/표지 선택 화면은 실제 폰의 XML과 캡처로 확인해야 한다. 예상 화면이 맞지 않으면 멈추고 화면을 반환하며, 추측 좌표 매크로로 진행하지 않는다. 모의 테스트 통과를 실폰 업로드 성공으로 간주하지 않는다.
- 현재 실폰 한 대에서 전용 사진첩의 영상 선택 → Edits 프로젝트 → 음악 추가·음악 볼륨 70 확인 → 내보내기 → Instagram 전달 → 본문·표지 입력 → 공유 1회 → 본인 프로필의 실제 게시물·게시 본문/오디오 → 리틀리 예약이 같은 표지의 실제 게시물로 연결되는 흐름을 확인했다. 완료 안내를 놓치면 `unknown`을 유지한 채 읽기 확인 후 `confirm-result`로 마무리했다. 실제 댓글에 따른 DM 전달은 별도 확인 대상이다. 다른 두 폰은 설정·작업 격리 테스트와 구분해 최초 연결부터 확인한다.

## 스킬명 없이 시작하는 사용 예시

이 저장소를 연 Codex에 아래처럼 요청한다. 설치된 스킬의 이름을 직접 지정하지 않아도 요청 내용에 맞춰 선택할 수 있다. 예시 자체는 실행 지시가 아니며 실제 사용자의 요청 범위로 진행한다.

| 이렇게 말하면 | 진행 범위 |
|---|---|
| “인스타 업로드 자동화 처음 써. 기존 설정 확인하고 초기 연결만 해줘.” | 설치·설정·로그인·폰 연결 준비. 게시하지 않는다. |
| “이 영상 인스타 업로드 준비해줘. 아직 게시하지 마.” | 지정한 한 편의 상품 확인·원링크·리틀리·Edits·작성기 검증까지. 최종 공유 전에 멈춘다. |
| “이 영상을 내 게시 계정에 올려줘. 리틀리부터 고정댓글까지 진행해줘.” | 대상 계정과 영상 확인 후 최종 공유·본인 댓글 작성/고정·리틀리 게시물 연결 확인까지. |
| “이미 올린 게시물의 준비된 댓글을 달고 고정해줘.” | 기존 게시물과 댓글 이력 확인 후 빠진 댓글/고정 단계만 수행. 영상은 재게시하지 않는다. |
| “새 Wi-Fi에 연결했어. 하던 업로드 이어줘.” / “새 폰을 추가해서 이 영상 올려줘.” | 해당 폰의 연결·식별자와 기존 공유 이력을 확인한 뒤 요청된 범위만 이어간다. |

영상·게시 계정·폰이 대화와 기존 작업에 있으면 재사용한다. 여러 대상 중 어느 것인지 알 수 없을 때만 필요한 선택을 묻고 임의의 최신 영상이나 새 계정으로 시작하지 않는다. `$hotpost-mobile-upload`는 원하는 경우 사용할 수 있는 직접 지정 방식이다.

## 처음 사용하는 사람의 초기 세팅

[간단한 시작 안내](MOBILE_UPLOAD_START.md)에 따라 저장된 설정·기존 Chrome 로그인·등록 폰·현재 완성 영상과 초안을 먼저 재사용한다. 아래 실행 전 확인으로 실제 계정과 연결을 대조하고, 빠진 로그인·폰 승인만 요청한다. 설치가 없을 때만 업로드 의존성을 준비한다. 새 PC 이전이나 VPN 서버 구축을 매 업로드의 선행 작업으로 추가하지 않는다. 초기 연결만 요청했다면 게시하지 않고, 대상 영상이 없는 경우 그 사실을 알린다.

## 초기 설정과 실행 전 확인

에이전트 진입점은 저장소 `skills/hotpost-mobile-upload/SKILL.md`다. **기존 설정을 먼저 조회하고 빠진 연결만 준비한다.** 저장된 계정·스토어·폰을 다시 등록하거나 초기화하지 않는다. 설치별 계정·스토어·컬렉션 입력과 로컬 저장 계약은 [초기 설정 화면](POST_PREPARATION_UI_20261022.md#설치별-초기-설정)을 따른다. 기존 설정에서 미리 채운 값도 재사용할 수 있지만 `configured`는 실제 로그인 성공이 아니다.

1. 스킬의 `scripts/preflight.py --repo <실제 clone> [--shortcode <영상 ID>]`를 저장소 Python으로 실행한다. 이 스크립트는 현재 설정, 폰 등록 유무, 기존 모바일 공유 이력과 리틀리 다음 게시물 소유권만 읽는다. 로그인·연결·예약·업로드를 실행하지 않는다. 기존 완료/불명 공유 이력이 있으면 현재 결과부터 확인한다.
2. 현재 자동화에 쓰는 **기존 Chrome 프로필과 열린 탭**부터 조회한다. 아래 항목을 실제 서비스 화면에서 대조한다. 저장된 프로필명/브라우저 식별값이 있으면 사용하고 이식 가능한 스킬에는 개인 프로필명·계정·태그·주소를 고정하지 않는다.

   | 서비스 | 실제로 확인할 것 |
   |---|---|
   | Instagram 웹 | 상품 확인·댓글용 로그인 계정. 모바일 게시 계정과 별도일 수 있다. |
   | 리틀리 DM 자동화 | 로그인된 관리 화면과 **연결된 게시용 Instagram 계정**, 기존 예약/자동화. 리틀리 로그인만으로 인스타 연동 완료를 가정하지 않는다. |
   | 쿠팡 인플루언서 | 로그인 계정의 본인 수익 태그, **내 스토어**에 표시된 공개 주소와 등록 컬렉션. 공개 스토어가 열린 것만으로 관리 로그인·소유 확인을 대신하지 않는다. 기존 쿠팡파트너스 탭의 인플루언서 진입점을 사용할 수 있다. |
   | 폰 Instagram·Edits | 등록된 폰의 실제 연결·식별자와 게시용 로그인 계정, 앱·미디어 권한. 폰 제어가 승인된 업로드 범위에서 확인한다. |

3. 모두 확인되면 초기 설정 요청을 반복하지 않는다. 빠진 서비스만 아래 문구에서 골라 한 번에 안내한다.

   > 자동화에 쓰는 기존 Chrome 프로필에서 Instagram(상품 확인용), 리틀리 DM 자동화, 쿠팡 인플루언서 ‘내 스토어’를 각각 열고 로그인해 두세요. 비밀번호나 인증 코드는 보내지 마세요. 로그인된 탭이 이미 있으면 그대로 쓰겠습니다.

   계정이 여러 개면 기존 설정과 대조해 수집용·게시용 역할을 구분한다. 탭 찾기·이동·누락값 확인은 에이전트가 처리하고 사용자에게는 직접 로그인·2단계 인증·필요한 연동 동의·폰에서만 가능한 승인만 요청한다. 자격 증명이나 쿠키를 스킬·설정·로그에 복사하지 않는다. 새 프로필·Ego 재생성으로 기존 로그인을 대체하지 않는다.
4. 계정/스토어/컬렉션 값이 없을 때만 확인된 값을 로컬 초기 설정에 저장한다. 기존 값과 다르면 대상·기존 작업 소유권을 확인하며 다른 사람의 설치 이력을 덮어쓰지 않는다. 리틀리 미연결·대상 계정 불일치·쿠팡 소유 미확인·폰 연결 실패는 해당 단계만 보류하고 확인한 항목과 필요한 사람의 조작을 기록한다.

초기 설정 점검이나 스킬 작성은 새 영상 업로드·중지된 수집/제작/예약의 실행 지시가 아니다. 실제 업로드는 아래 한 편 절차와 현재 사용자 요청 범위에 따른다. 초기 연결 완료, 업로드 완료, 리틀리 게시물 연결 완료, 댓글→DM 실제 전달 완료는 각각 구분해 보고한다.

## 폰에서 필요한 정보

1. 휴대폰 WireGuard 내부 IP.
2. 개발자 옵션 → 무선 디버깅 화면의 **연결 포트**. 페어링 포트와 다를 수 있다.
3. 처음 연결할 때 페어링 포트와 폰에 표시되는 일회용 코드/승인. 코드는 PC의 프롬프트로 입력하고 저장하지 않는다.

WireGuard는 네트워크 경로이며 ADB를 켜거나 권한을 부여하지 않는다. Android 무선 디버깅의 Wi-Fi 요구·서비스 바인딩은 폰/OS에 따라 확인해야 한다. 모바일 데이터에 VPN만 켰다고 ADB 수신이 보장되는 것은 아니다. 이 구현은 `adb tcpip 5555`, 공개 포트 개방, 루팅, 잠금 해제, 인증 우회를 자동 수행하지 않는다. 휴대폰 버전/식별자는 연결 후 읽으므로 사전에 따로 적을 필요는 없다.

## 연결 준비와 에이전트 지침

사람이 따라 하는 설치·페어링·재연결·문제 해결은 [휴대폰 연결 가이드](PHONE_SETUP.md)가 원본이다. 저장소 루트의 `phone-pair.cmd`(최초 등록)와 `phone-reconnect.cmd`(연결 포트 변경)를 탐색기에서 더블클릭해 사용한다.

- 페어링 코드는 사용자가 `phone-pair.cmd` 창에 직접 입력한다. 에이전트는 코드를 채팅으로 요청하거나 대신 입력하지 않는다. 사용자가 채팅에 코드를 보냈다면 사용하지 말고 팝업의 새 코드로 창에 입력하도록 안내한다.
- AI 앱의 내장 터미널 패널은 대화형 입력(getpass·`adb pair` 프롬프트)을 전달하지 못한 사례가 있다. 대화형 입력이 필요하면 패널 대신 더블클릭 스크립트를 안내한다.
- 사용자에게는 필요한 값만 묻는다. 최초 등록은 폰 WireGuard IP·연결 포트·페어링 포트이고, 재연결은 새 연결 포트 하나다(`configure --adb-port N` 후 `connect`). 폰 WireGuard IP는 Wi-Fi가 바뀌어도 유지된다.
- 에이전트는 PC의 기존 설정·VPN 경로·ADB 연결 목록과 mDNS 발견 결과부터 확인하고, 가능한 진단·포트 갱신·연결·패키지 준비·전송·작성기 입력을 직접 처리한다. 발견된 주소도 등록된 VPN 대상·기기 확인 규칙을 따른다. 폰에서만 가능한 Wi-Fi/무선 디버깅 켜기·새 네트워크 허용·현재 포트 확인·잠금/인증만 사용자에게 요청하며, 사용자가 터미널 명령이나 재연결 스크립트를 대신 실행하도록 일괄 넘기지 않는다.
- 업로드 시작·재개 시 새 Wi-Fi로 이동했거나 연결이 끊겼다면 [새 Wi-Fi 재연결 절차](PHONE_SETUP.md#새로운-wi-fi로-이동한-경우)를 먼저 따른다. 폰의 Wi-Fi·양쪽 WireGuard·무선 디버깅·새 네트워크 허용·현재 연결 포트를 확인하고 기존 페어링과 폰 식별자를 유지한다. `doctor`의 설정 확인을 실제 연결 성공으로 해석하지 않는다. 새 Wi-Fi 접속만으로 재페어링하거나 저장된 VPN IP를 Wi-Fi IP로 바꾸지 않는다.
- 페어링 실패 원인은 `%TEMP%\adb.log`로 좁힌다. `Failed to decrypt`는 틀린 코드, `CERTIFICATE_UNKNOWN`은 미페어링 연결 시도다.
- 연결·`doctor`·캡처는 게시 승인이 아니다. 아래 절차의 명시 승인 규칙을 그대로 따른다.

## 로컬 사용법

저장소 루트에서 실행한다. 기존 폰 `primary`는 Git 제외 `data/.mobile-device.json`, 추가 폰은 `data/mobile-devices/<이름>.json`을 사용한다. 작업/캡처/영수증은 `data/mobile-reels/`에 남는다. [여러 폰 등록·선택](PHONE_SETUP.md#여러-폰-등록선택)에 따라 `--device phone2`처럼 선택한다. 작업 ID가 있는 명령은 그 작업의 폰을 자동 선택하며 다른 기기 지정은 거절한다. 참고 설정은 `docs/mobile-device.example.json`이다.

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-mobile.txt
.venv/Scripts/python.exe -X utf8 -m hotpost.mobile_reels_cli doctor
.venv/Scripts/python.exe -X utf8 -m hotpost.mobile_reels_cli configure --phone-ip PHONE_VPN_IP --adb-port CONNECT_PORT
.venv/Scripts/python.exe -X utf8 -m hotpost.mobile_reels_cli pair --pairing-port PAIR_PORT
.venv/Scripts/python.exe -X utf8 -m hotpost.mobile_reels_cli connect
```

페어링은 PC·폰 조합마다 한 번만 한다. 설정/진단은 연결 또는 업로드가 아니다. 실제 제어는 매번 해당 IP로 가는 WireGuard 인터페이스, 지정 TCP 포트, ADB 인증과 휴대폰 식별자를 다시 확인한다. 폰의 무선 디버깅 연결 포트가 바뀌면 `configure --adb-port N`(IP 생략) 후 connect로 갱신하며, 이때 저장된 폰 IP·기기 식별자 확인은 유지된다. `--phone-ip`를 주면 새 등록으로 보고 다음 connect에서 식별자를 다시 저장한다. `--vpn-network`를 생략하면 이 PC의 WireGuard 어댑터 대역 중 폰 IP를 포함하는 대역을 쓴다. pair는 콘솔이면 getpass로, 파이프면 표준입력 한 줄로 코드를 받는다. VPN 설정/개인키는 읽거나 변경하지 않는다.

## 한 편 업로드 순서

**리틀리 자동화를 먼저 완료하고, 그 뒤 모바일 업로드를 진행한다.** 로컬 영상·본문 준비는 먼저 할 수 있지만 폰 전송·Edits 편집/내보내기·Instagram 작성기 진행은 리틀리 저장 확인 뒤에 한다. [리틀리 설정 절차](MONETIZATION_PLAN_20261015.md#114-리틀리-등록-사용자가-제공한13단계-고정-루틴)의 다음 게시물·모든 댓글·답글 추가 2회 조건을 사용하며, DM 메시지·버튼 문구는 최신 [게시물 문구 규칙](POST_COPY_RULES.md)을 따른다. 버튼은 실제 UI 제한도 확인한다.

선행 확인은 해당 업로드 계정, 현재 영상의 정확한 상품/옵션과 본인 수익 링크의 실제 연결 검증, 저장된 DM/버튼 URL, 다음 게시물 모드·모든 댓글 조건·답글 설정·활성/예약 상태·자동화 식별값을 포함한다. 등록 클릭만으로 완료 처리하지 않는다. 한 계정의 다음 게시물 예약을 다른 영상과 섞지 않고 기존 자동화를 먼저 조회한다. 상품 링크나 저장 결과가 없거나 불명확하면 폰 진행을 보류하고 필요한 선행 단계부터 처리한다. 레퍼런스 댓글/DM 요청은 해당 대상의 사용자 승인과 기존 1회 시도 기록을 확인한 뒤에만 수행한다.

리틀리에 쓸 쿠팡 링크는 **우리 원링크 시스템 `hotpost.coupang_onelink`를 통해 확보한 본인 스토어 원링크**를 사용한다. 기존 스토어에 정확한 상품/옵션이 있으면 이를 재사용하고 `link_identity`의 `AFFSDP / CREATOR` 형식·본인 수익 태그와 실제 랜딩의 상품/옵션을 확인한다. 파트너스 화면에서 직접 만든 `/a/` 단축 링크만으로 이 단계를 완료 처리하거나 원링크를 대체하지 않는다. 이미 저장한 리틀리의 링크를 교정할 때에는 같은 자동화를 수정하고 메시지·발송 조건·답글을 보존한 채 다시 읽어 검증한다.

상품 확인은 **① 같은 게시물의 기존 검증 결과·수신 DM·상품/원링크 기록 재사용 → ② 원작 본문·프로필의 공개 상품 링크와 상품 번호 확인 → ③ 앞선 경로로 정확한 상품/옵션을 확정할 수 없을 때만 승인된 키워드 댓글 1회·모바일 수신 DM 확인** 순서다. 기존 결과도 현재 대상과 상품/옵션·본인 태그가 맞는지 확인한다. 공개 링크로 확정했으면 댓글/DM 요청을 추가하지 않는다. 원작성자에게 임의의 직접 DM을 먼저 보내는 절차가 아니다.

댓글→수신 DM 경로의 댓글 제출은 기존 수집 Chrome에서 처리할 수 있지만, **수신 DM의 상품·팔로우 확인 버튼은 모바일 Instagram에서 확인·조작한다.** PC에서 버튼이 보이지 않는다고 DM 미수신·버튼 부재로 바로 판정하거나 댓글을 다시 보내지 않는다. 수집 계정과 같은 모바일 계정/원작성자 대화를 확인하고 같은 1회 시도의 버튼 조작·결과를 기록한다. 이 선행 DM 작업은 업로드 작성기를 진행하는 작업과 구분하며, 저장된 업로드 초안은 보존한다.

본인 스토어 등록이 필요하면 기존 공개 컬렉션의 상품 수·상품/옵션 목록을 먼저 보존하고 편집 화면의 전체 목록과 대조한다. 공개 수와 편집 수가 다르면 상품 추가/최종 저장을 진행하지 않는다. 판매 종료 항목이 화면에서 빠졌더라도 기존 항목 제거를 승인한 것으로 해석하지 않는다. 저장 뒤에는 새 상품뿐 아니라 기존 항목의 보존도 확인한다. 실제 누락을 발견하면 추가 전체 저장을 중지하고 원래 식별값으로만 복구를 시도하며, 서비스 거절·미확인은 별도 오류로 남긴다.

이미 모바일 초안을 만든 뒤 선행 누락을 발견하면 기존 작업·영상·음악·볼륨·초안을 보존한다. 해당 작업의 `upstream_hold`에 리틀리 보류 사유와 재개 조건을 남기면 폰 변경과 공유 claim을 재시작 후에도 거절한다. `status`·`inspect`·공유 시도 후 읽기 결과 확인은 유지한다. 실제 리틀리 저장 근거를 작업 폴더에 남기고 같은 계정/영상/상품 링크를 확인한 뒤에만 보류를 해제한다. 해제 뒤 현재 화면·본문·표지를 다시 검토해 새 `ready` 승인을 만들며 과거 승인값으로 바로 공유하지 않는다.

이 경우 `bind-littly JOB --receipt RECEIPT_JSON`은 현재 초안의 본문·영상·표지와 리틀리 저장 결과의 계정·영상·초안 버전·원링크·DM/버튼·실제 저장 근거 해시를 대조한다. 원래 입력 패키지는 바꾸지 않고 별도 검증 파일을 결속해 보류·과거 승인을 해제한다. 새 승인에는 이 결속도 포함하며 근거 파일이 바뀌면 거절한다. 새 작업 생성·재변환·재전송으로 대체하지 않는다.

시작·재개 전 위 연결 준비를 마치고 실제 `connect` 성공을 확인한다. 기존 작업이 있다면 `status JOB`와 재연결 후 `inspect JOB`로 현재 단계·화면·계정을 확인하며, 연결 복구를 이유로 새 작업 생성·작성기 재시작·공유 재시도를 하지 않는다. 공유 시도 뒤 결과가 불명확하면 아래 9번의 읽기 확인부터 진행한다.

1. 게시물 준비에서 본문/표지/계정을 정하고 `prepare SHORTCODE --account <이 설치에 등록한 게시 계정>`으로 한 계정의 패키지를 만든다. 이것은 게시가 아니다. 현재 active 영상/표지/원음 규칙/선택 문구/초안 버전·본문/댓글/링크를 결속하며 파일을 복사해 고정한다. 영상에 광고 표시와 감탄사 없는 낭독 대본이 있어야 한다. Android 호환 영상은 별도로 변환하고 원래 편집본은 보존한다.
2. `transfer JOB`는 폰의 `/sdcard/Movies/Hotpost/JOB/`에 영상/표지를 보내고 실제 SHA256을 확인한다. MediaStore에 등록된 해당 영상의 content URI 하나만 사용한다. 갤러리 등록이 늦으면 다시 확인하며 임의의 최신 영상을 선택하지 않는다.
3. `app instagram`으로 앱을 열고 폰의 **본인 프로필**에서 업로드 계정을 확인한다. `inspect JOB`가 현재 화면의 요소/번호/해시 및 로컬 PNG/XML을 저장한다. `navigate JOB --node INDEX --screen-sha HASH`는 그 화면에서 관찰된 다음/릴스/프로필/표지 등의 요소만 누른다. 계정 전환도 실제 화면에서 수행한다.
4. 기본은 **Edits에서 준비하고 Instagram으로 넘기는 경로**다. `open JOB` 또는 `open JOB --via edits`는 Instagram 본인 프로필에서 계정을 확인한 뒤 Edits를 연다. 보이는 새 프로젝트 → 갤러리 → 작업 ID와 같은 전용 사진첩으로 이동하고 `select-edits-video JOB --screen-sha HASH`로 해당 사진첩의 영상 하나를 선택한다. MediaStore URI를 전송 기록과 대조하며 임의의 최신 영상을 고르지 않는다. SEND 요청 성공이나 앱 실행만으로 작성기 진입을 완료 처리하지 않는다. 이미 연 작업은 현재 화면부터 이어간다. `--via instagram` 구현은 호환용으로 보존하며 별도 지시 없이 기본 업로드 경로로 선택하지 않는다.
5. Edits에서 영상 분위기에 맞는 음악을 선택하고 **추가 음악 볼륨 70%**를 기본으로 한다. 기존 영상의 내레이션 볼륨과 ‘모든 오디오 클립에 볼륨 적용’은 바꾸지 않는다. 실제 목록의 곡명·아티스트·트랙 ID를 읽고 선택하며, 음악 목록의 전용 해시와 ID를 `select-edits-audio`로 결속한다. 배경 타임라인 재생 시각을 음악 목록 변경으로 오인하지 않되 실제 검색어·곡 목록·위치 변경은 다시 확인한다. 볼륨 화면의 숫자가 `70.0`인지 확인한 뒤 `record-edits-volume JOB --percent 70 --screen-sha HASH`로 기록하고 확인 버튼을 누른다. 다른 값 요청은 해당 작업에 명시해 기록한다. 수치 설정·시각 확인을 실제 청감 승인으로 표현하지 않는다. 음악·볼륨 검증 후 Edits의 다음/내보내기 → 공유 위치의 Instagram으로 이동한다. 이것은 Instagram의 최종 공유 버튼과 구분한다.
6. Instagram에서 `fill-caption JOB`로 본문을 입력하고 직접 읽은 문자열을 원문과 대조한다. 일부 폰의 XML은 이모지를 점으로 바꾸므로 XML 표시만으로 본문 손상·일치를 판단하지 않는다. 커버 수정 → 카메라 롤에서 추가 → 작업 전용 사진첩을 선택하고 `select-cover JOB --screen-sha HASH`로 전송한 표지 한 장의 실제 파일 SHA를 확인해 선택한다. 최종 작성 화면의 표지를 준비된 cover.png와 **시각 비교한 후** `review-cover JOB --screen-sha HASH --cover-sha COVER_SHA`로 기록한다. 이것은 이미지 자동 인식 성공 주장이 아니라 작업자의 검토 영수증이다.
7. `ready JOB`는 현재 계정 헤더·정확한 본문·릴스 작성 화면·공유 버튼·표지 검토를 확인하고 공유 직전 캡처와 패키지 SHA를 기록한다. 여기까지 실제 게시하지 않는다.
8. 사용자가 해당 계정/영상의 실제 게시를 지시한 뒤 `ready` 결과의 `approval_sha256`을 넣어 `publish JOB --approved-package-sha APPROVAL_SHA`로 공유를 한 번 실행한다. 대상 계정·영상이 확정된 업로드 요청이나 검토한 절차에 대한 실행 지시가 있으면 같은 범위의 게시 승인을 반복 요청하지 않는다. ‘업로드 준비’는 공유 직전까지만 진행하며, 문서 구현·연결 진단만 요청한 경우 실제 게시를 실행하지 않는다. 승인 근거가 되는 사용자 지시와 대상은 로컬 실행 기록에 보존한다.
9. 공유 완료 메시지를 확인하면 submitted로 기록한다. 전송 이후 연결이 끊기거나 성공 안내가 불명확하면 unknown으로 영속 보류한다. `reconcile JOB`는 읽기 확인만 하고 다시 공유하지 않는다. 앱/프로필에서 실제 게시를 확인한 운영자는 현재 화면과 우리 릴스 URL로 `confirm-result JOB --post-url URL --screen-sha HASH`를 명시 기록할 수 있다. 원본 레퍼런스 URL은 허용하지 않는다. 이 역시 공개된 인코딩 영상의 픽셀 동일성을 인증하지 않는다.

하나의 폰 작성기는 한 영상이 소유한다. CLI 사이에도 소유권이 DB에 남으므로 다른 영상이 작성 화면을 덮어쓰지 않는다. `cancel JOB`는 공유 전 작업만 해제할 수 있고 자료를 삭제하지 않는다. 공유를 시도한 작업은 재시작/시간 경과/취소로 재게시 잠금이 풀리지 않는다. 같은 입력의 prepare는 기존 작업을 반환한다.

기기마다 설정·실제 식별자·실행 잠금·작성기 소유권을 분리한다. 기존 폰의 설정과 작업은 이동하거나 초기화하지 않는다. **같은 계정+영상의 공유 시도 이력은 전체 기기에서 함께 확인**하므로, 다른 폰에서 새 작업을 만들어도 불명/제출/완료 시도를 재게시하지 않는다.

앱 버전상 최종 작성 화면에 계정 헤더가 없으면, 같은 Edits 전달에서 Instagram이 직접 표시한 `계정명님으로 로그인함` 안내와 릴스 작성 화면의 저장된 캡처를 `record-handoff-account JOB --screen-label LABEL`로 결속할 수 있다. 앞선 본인 프로필 확인·동일 전달 시각·캡처/이미지 SHA가 필요하며, 본문 속 계정 언급은 근거가 아니다. 계정 전환이나 새 전달은 기존 근거를 무효화한다. 검토 승인 식별값 `approval_sha256`은 입력 패키지뿐 아니라 Edits의 선택 영상·음악·볼륨·전달과 공유 직전 화면에도 결속한다. Edits 결과를 원래 입력 영상과 바이트가 같은 파일이라고 주장하지 않는다.

고정댓글/제품 링크는 패키지에 보존한다. **실제 게시 확인 뒤 본인 고정댓글 작성·고정까지가 업로드 절차다.** 아래 절차를 완료해야 고정댓글 완료로 표시한다. 리틀리 선행 작업은 기존 로그인 Chrome에서 수행하고 실제 저장 근거를 남긴다. 게시 뒤 리틀리가 의도한 우리 게시물에 연결됐는지 별도로 확인한다. Instagram 비공개 API, 로그인 정보 복제, 자동 CAPTCHA/비밀번호 입력을 사용하지 않는다.

## 게시 후 본인 댓글 작성·고정

1. 원작 레퍼런스가 아닌 **실제 게시된 우리 릴스 URL·게시 계정**과 현재 폰의 댓글 작성 계정을 확인한다. 원본 업로드 패키지의 `pinned_comment`를 사용하고 최신 초안과 다르면 보존한 요청·수정 이력으로 적용할 버전을 확정한다. 빈 문구나 불명확한 대상에 새 댓글을 만들지 않는다.
2. 기존 댓글과 해당 작업의 작성 시도/결과 기록을 먼저 확인한다. 본인 계정의 같은 문구가 있으면 재작성하지 않고 그 댓글을 사용한다. 없을 때만 입력하고 실제 Unicode 문자열·줄바꿈을 대조한 뒤 제출 전 기록을 남겨 **댓글 게시를 한 번** 실행한다. 키보드가 입력칸/버튼을 가리면 접고 현재 화면을 다시 확인한다. 제출 결과가 불명확하면 재전송하지 않고 같은 게시물의 댓글 목록부터 확인한다.
3. 댓글 작성자·실제 표시 문구를 확인하고, **그 댓글을 길게 누른 뒤 나타난 메뉴의 ‘고정’을 누른다.** 추가 안내가 있으면 현재 문구와 대상을 확인해 정상 절차를 따른다. 다른 댓글을 삭제하거나 고정 해제로 바꾸지 않는다. 이미 고정됐으면 조작을 반복하지 않는다.
4. 댓글 목록을 다시 열어 같은 본인 댓글의 **‘고정됨’ 표시/핀 표시**를 확인한다. 필요하면 길게 누른 메뉴가 ‘고정 취소’/‘고정 해제’로 바뀐 것도 읽어 확인하되 누르지 않는다. 단순히 댓글 작성이나 고정 클릭이 성공한 것만으로 완료 처리하지 않는다.
5. 실제 우리 게시물 ID/URL·작성 계정·댓글 문구/해시·제출 시도·작성 확인·고정 확인·스크린샷을 Git 제외 작업 기록에 남긴다. 댓글 ID가 실제 화면에 없으면 만들어내지 않는다. 업로드 완료와 댓글 작성 완료·고정 완료를 구분하며 고정이 막히면 해당 단계만 보류한다. 영상을 다시 올리지 않는다.

본인 고정댓글은 게시 절차이며 레퍼런스 상품 확인용 댓글이나 리틀리 자동 답글과 별개다. 본인 댓글 작성만으로 실제 이용자의 댓글→DM 전달까지 검증됐다고 보고하지 않는다. 모바일 CLI의 `publish`는 영상 공유까지만 처리하므로, 이 후속 단계는 실제 앱 화면을 통해 별도로 실행·검증한다. 기존 게시 지시의 같은 영상/계정/준비 문구 범위에서는 일상적인 승인을 반복 요청하지 않는다.

## 코드와 검증

- `mobile_device.py`: 장치 설정, WireGuard 경로/포트 확인, 명시 ADB 대상, 일회용 페어링, 파일 해시 전송, 화면/요소/Unicode 입력.
- `mobile_reels.py`: 최신 게시물 패키지 동결·호환 변환, 폰 소유권, 작성 화면 검증, 단 한 번의 공유와 불명 결과 보존.
- `mobile_reels_cli.py`: PC에서만 사용하는 명령 진입점. 다른 제작/수집/예약 실행기를 시작하지 않는다.
- `tests/test_mobile_reels.py`: 전송·화면·계정/본문 검증·공유 후 실패·재시작 중복 방지·패키지 변경·실제 대상 명령 인자 격리 fixture.
- PC 확인 근거: `data/mobile-reels-implementation-20261023/`.

실제 화면은 기기 연결 후 위 절차로 캡처하고 조정해야 한다. 코드/모의 검증·PC 변환 시험과 실폰 실행 근거를 구분한다. 위에서 확인한 실폰 한 대의 게시·리틀리 연결 성공을 다른 기기의 연결 성공이나 실제 댓글→DM 전달 성공으로 확대하지 않는다.
